① 这段材料到底在说什么

一句话本质：软件交付生命周期（Software Delivery Lifecycle）描述的是一项软件改动怎样从“想法/需求”一路变成“可安全运行、可追责、可回滚的线上结果”。它关心的不只是写代码，而是整条交付链路：实现、验证、构建、验收、发布、部署、观测与恢复。

AI Coding 时代最重要的变化：过去人类常常既写代码、又点页面、又看日志、又跑命令。现在应把可重复、可机器判定、可留证的工作尽量交给 AI Agent + 自动化工具，让人把注意力放在需求语义、风险边界、验收授权和异常决策上。

上位概念

软件工程（Software Engineering）：用系统化方法设计、构建、验证、交付和维护软件。

当前概念

Software Delivery Lifecycle：从可执行需求到可运行版本，再到运行反馈与恢复的端到端交付过程。

下位机制

开发反馈循环、质量保证、构建打包、持续集成、持续交付/部署、发布治理、可观测性与回滚。

容易并列混淆

Software Development Life Cycle 往往覆盖需求、设计、开发、测试、维护等更广生命周期；CI/CD Pipeline 则只是 Delivery Lifecycle 中的一组自动化机制。

学习依赖：Git / 分支 + 测试基本概念 + 开发/测试/生产环境 → Software Delivery Lifecycle → CI/CD、Release Engineering、Site Reliability Engineering、Platform Engineering。

② 你必须先认识的概念

只学真正决定交付方式的 8 个术语。每张卡都回答“直觉—当前案例—边界”。

Software Delivery Lifecycle
直觉
把一次改动从需求、实现、验证一直送到线上并持续观察的完整道路。
当前案例
它是本课主轴：所有‘要不要构建、谁来测、什么时候人工确认’的问题都放回这条生命周期判断。
边界
它不是某一个 Jenkins/GitHub Actions 文件，也不是某一次部署命令。
Feedback Loop
直觉
你改完东西后，多快能得到‘对/不对’的反馈。反馈越快，错误越便宜。
当前案例
日常开发默认追求秒级到分钟级反馈：HMR、定向测试、API smoke、少量 Playwright，而不是每次都跑完整生产发布链。
边界
快反馈不代表最终可发布；它解决的是开发速度，不替代候选验证。
Quality Assurance / Verification
直觉
用证据证明软件满足已经定义好的技术条件，例如测试通过、接口契约一致、权限没有越界。
当前案例
AI/CI 应承担绝大多数 QA：自动执行测试、检查日志、比较结果、生成结构化证据。
边界
QA 证明‘检查项通过’，但不能自动等价成‘业务负责人已经接受这个结果’。
Acceptance
直觉
有权的人基于约定的验收标准和证据，对某个具体候选版本作出接受或拒绝。
当前案例
人类不必重做 AI 已经做过的 200 个检查，而应确认：验收对象是谁、证据是否完整、关键风险是否覆盖，然后给出可追踪的 ACCEPTED / REJECTED。
边界
Acceptance 是治理与授权动作，不等于‘我随手点了几下觉得能用’。
Continuous Integration (CI)
直觉
每次代码变化都自动合并验证：编译、测试、静态检查、契约检查等尽早发现问题。
当前案例
AI 提交候选后，由 CI 重跑可复现门禁，避免只相信 Agent 自己口头说‘我测过了’。
边界
CI 不是生产部署；它主要解决‘候选代码是否经得起统一检查’。
Continuous Delivery / Deployment
直觉
Continuous Delivery 让软件始终处于可发布状态；Continuous Deployment 更进一步，让通过门禁的版本自动进入生产。
当前案例
是否全自动上线取决于风险等级。低风险可自动，高风险可保留人工验收门。
边界
CD 不是‘所有项目都必须无人值守上线’，而是让发布过程可重复、可自动化、可控制。
Artifact
直觉
从某个确定提交构建出来、准备被发布的不可变产物，例如镜像、前端静态包、二进制包。
当前案例
验收应绑定具体 commit + artifact，而不是验收 A 版本、部署时又临时重新构建出 B 版本。
边界
Artifact 不是源码目录本身；发布治理强调‘我验收的就是我部署的’。
Observability & Rollback
直觉
Observability 是上线后用日志、指标、追踪和业务信号看系统是否真的健康；Rollback 是出问题时快速回到已知安全版本。
当前案例
交付并不在 deploy 成功时结束。AI 可持续做 smoke、健康检查和异常归因，人类只在风险越界时介入。
边界
没有观测和恢复能力的‘自动部署’，只是把风险自动化地推到线上。
Connect

③ 概念关系与最小知识闭包

把交付过程看成一条证据不断增加、自由度不断减少的状态链。越靠后，越不能“随便改一下再说”。

状态机

可以把交付抽象成：DRAFT → IMPLEMENTED → VERIFIED → CANDIDATE → ACCEPTED → RELEASED → OBSERVED。任何一步失败都回到前一安全状态，而不是靠口头解释跨级。

一个核心谓词

只有当“代码证据通过 + 验收合同满足 + 风险门禁满足”时才允许发布：

release_allowed = qa_ok ∧ contract_ok ∧ risk_gate_ok

三个不变量

① 验收必须绑定具体 commit；② 验收的 artifact 就是部署的 artifact；③ 每个上线动作都有可观测证据和恢复路径。

这也是 AI Coding 的工程化边界：AI 可以非常擅长生成实现和运行检查，但“什么叫正确、哪些风险必须由谁承担、什么版本被正式接受”必须被合同化、证据化和授权化。

④ 把真实案例重新还原

假设 AI Agent 收到一个真实 Web 管理端任务：新增“删除用户”能力，修改前端页面、后端 API、权限判断和一条数据库 migration。你不希望自己每改一次就手点 20 个页面，于是把交付拆成三层。

Layer A · 日常开发反馈：不需要先做生产构建

环境
隔离数据库 + 本地/测试 API + Vite dev server / HMR。Docker 不是目的；只要依赖可控、数据隔离、服务可复现，就可以选择更轻的启动方式。
AI 自动做
改代码 → 跑定向 unit/integration → API smoke → Playwright 验证关键路由 → typecheck/lint → 读取失败证据 → 自动修复再重跑。
人的动作
通常不点。只在需求语义模糊、视觉主观判断、危险权限边界等机器不容易判定的地方介入。
需求 / AC
  ↓
AI 修改代码
  ↓
Dev Server + HMR
  ↓
API smoke + targeted tests + Playwright
  ↓
失败 → AI 修复 → 重跑
  ↓
通过 → 形成候选

Layer B · 候选验证：准备提交或发布时才跑“重流程”

这里追求的不是最快，而是完整、可复现、可留证。典型门禁包括：完整测试、生产构建、migration 验证、跨租户/权限测试、静态检查、依赖/安全检查、OpenAPI 或 schema 漂移检查、构建产物摘要。

关键原则：开发时可以“不构建就看效果”；但正式候选必须证明“生产构建真的能出来”。这就是开发反馈与发布证明分层。

Layer C · 发布与验收：人类完成闭环，而不是人工复测一遍

AI/CI 给出结构化证据：候选 commit、artifact digest、测试矩阵、失败为 0、风险项、已知限制、回滚版本。人类只需要对验收对象和风险作判断，并留下 ACCEPTED / REJECTED。

适合 AI

重复点击、回归测试、截图比对、接口 smoke、日志检索、权限矩阵、构建、部署 smoke、证据汇总。

适合人

需求是否真的满足业务、危险写操作是否可接受、视觉/体验是否达标、例外风险是否接受、最终授权。

⑤ 概念如何映射到现实

你看到的工程动作在 Delivery Lifecycle 里的位置默认谁做为什么
Vite / UniApp dev / Flutter hot reload开发反馈层AI 启动与使用；人按需观察目标是快速验证改动，不是发布证明。
API smoke / unit / integration开发反馈 + 候选验证AI / CI高度可重复、机器判定明确，人工重复执行没有价值。
Playwright 关键路由验收开发反馈 + 自动 QAAI / CI浏览器点击本身可以自动化；人只看异常证据和高风险语义。
生产 build / bundle / migration候选验证层AI / CI重，但必须在候选阶段证明生产路径可用；不应每次小改都跑。
人工 UAT / Acceptance发布验收层有权的人不是重复 QA，而是确认业务语义、风险、证据和授权。
Release / Deploy发布执行层流水线为主应可重复、可追踪、可回滚，避免人工 SSH 点击和手抄命令。
Smoke / metrics / logs / rollback运行反馈层AI 监测，人处理越界风险上线不是终点；健康必须通过真实运行证据确认。

QA、验收、开发环境工程、发布流程到底分别属于哪里？

开发环境工程

解决“怎么低成本得到反馈”：dev server、HMR、Mock/Proxy、隔离数据库、本地 API、测试数据、可复现依赖。

QA / Verification

解决“怎么证明技术条件成立”：测试策略、测试金字塔、E2E、契约、静态分析、安全检查、证据。

Acceptance

解决“谁有权宣布这个候选满足验收合同”：UAT、acceptance criteria、审批、签字/记录、风险接受。

Release / Deployment

解决“怎样把已接受的 artifact 稳定送到目标环境”：CI/CD、发布策略、灰度、回滚、观测。

真正该减少的“点击”：人肉逐页面回归、人肉重复跑命令、人肉看每条日志、人肉复制构建包、人肉 SSH 部署。不该减少的，是对目标、风险、责任和最终接受的判断。

⑥ 现在把它当成一道题

1场景：AI Agent 已完成一个“管理员删除用户”的前后端功能。它在开发环境里通过了 18 个 unit/integration tests、API smoke、6 条 Playwright 路由，并且 typecheck/lint 全绿。一个同事又手动点了 12 个页面，说“看起来没问题”。但是目前还没有跑生产 build、migration 演练、跨租户权限测试，也没有生成可绑定 commit 的候选 artifact。

问题：你现在是否应该让这个版本直接上线？请设计一条合理的 Software Delivery Lifecycle，至少回答四点：

  1. 哪些检查留在日常快速反馈层？
  2. 进入候选前必须再补哪些自动化证据？
  3. 人类最终应该验什么，而不是重复点什么？
  4. 部署后怎样证明“真的安全”，以及失败如何恢复？

Hint → Answer

⑦ 分级提示，最后就是实际答案

Hint 1 · 方向

先不要按“测试多不多”判断。把问题拆成三个目标：快反馈、候选证明、发布授权。现在已有证据大多只覆盖第一个目标。

Hint 2 · 结构

尝试画出状态：IMPLEMENTED → VERIFIED → CANDIDATE → ACCEPTED → RELEASED → OBSERVED。问自己：目前缺的是哪几个状态转换所需的证据？

Hint 3 · 接近答案

至少要补：生产 build、migration、跨租户/权限、完整门禁、commit + artifact 绑定；人工验收应聚焦删除语义、权限风险、恢复能力和证据是否完整，而不是再把那 12 个页面手点一遍。

答案 · 实际答案

不应该直接上线。现有结果说明开发反馈不错，但还没有形成可发布候选。

1 · 日常反馈层

保留 dev server/HMR、定向 unit/integration、API smoke、关键 Playwright、typecheck/lint。AI 失败就自动修复并重跑。这里不要求每次生产 build。

2 · 候选验证层

AI/CI 补跑生产 build、完整测试矩阵、migration up/down 或演练、跨租户与越权测试、删除幂等/重复请求、schema/契约检查、安全与依赖门禁，并产出 commit、artifact digest、结构化测试结果。

3 · 人工验收层

人确认“删除”的业务语义是否符合合同、谁有权限、误删如何恢复、审计是否完整、已知风险是否接受；必要时只做少量高价值探索性验证。然后把 ACCEPTED/REJECTED 绑定到具体候选，而不是重新人工回归全部页面。

4 · 发布与运行层

流水线部署已经验收的同一 artifact；部署后自动跑 smoke、权限探针和健康指标。先灰度/小流量更安全；若错误率、权限异常或业务指标越界，自动停止并回滚到上一个已知安全 artifact。

最终心智模型：AI 负责把“实现 + 检查 + 证据”尽量自动化；CI/CD 负责让证据可复现、让发布可重复；人类负责定义正确性、确认高风险语义、接受或拒绝具体候选。这样减少的是低价值点击，而不是减少责任。
