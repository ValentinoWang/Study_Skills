Git 三个状态为什么会不一致？

把“本地前端分支、GitHub main、106 服务器 checkout”当成一次真实发布诊断题。目标不是背命令，而是先建立 Git 的状态模型，再决定谁该保护、谁该同步。

Git / DevOps/learn15–20 min中等
学习进度：
目录01 先看懂02 核心术语03 状态图04 案例还原05 训练题06 分级提示

① 这段材料到底在说什么

一句话：你现在不是简单地“有三份代码”，而是有多个 Git 指针停在不同 commit 上；GitHub 的 main、106 的 origin/main、106 当前 HEAD、本地前端分支，各自回答的是不同问题。

最容易混淆：
工作树干净 ≠ 代码是最新的
origin/main 已更新 ≠ 服务器当前 checkout 已更新

② 你必须先认识的概念

HEAD
直觉：你此刻“站在哪个提交上”。
严格一点：HEAD 是当前 checkout 所指向的分支或 commit。服务器实际工作目录通常由它决定。
比喻：书桌上真正摊开的那一版教材。
origin/main
直觉：本地仓库对“远程 main 最近位置”的记忆。
严格一点：它是 remote-tracking branch，由 fetch/pull 等操作更新。
关键：它更新并不会自动把当前 HEAD 切过去。
工作树干净
直觉：当前 checkout 上没有尚未提交的文件修改。
不是：“已经与 GitHub 同步”或“正在运行最新版”。
merge base / ahead / behind
merge base：两条历史最近的共同祖先。
ahead/behind：相对另一条历史而言，双方各自有多少独有提交。它不是分支自身固定属性。
worktree
同一个 Git 仓库可以同时摊开多个独立工作目录。某个临时 worktree 落后 7 个提交，只描述那张“工作桌”，不代表整个项目或服务器都落后 7 个提交。

④ 真实案例还原

事实

GitHub main：84382576。106 的 origin/main 也是这个 SHA。

事实

106 当前 checkout：wip/server-local-20260831 @ c5e35ae，工作树干净。

事实

106 相对 GitHub main：GitHub 有 631 个独有提交，106 有 1 个独有提交。

事实

本地前端分支：a0580dec，尚未推送、尚未合入 GitHub，也未进入 106。

事实

前端分支与 GitHub main 的共同基线为 36b470e7；GitHub +621，前端 +66。

事实

把当前 GitHub main 与前端分支合并，会冲突 48 个文件。

真正风险：在还没识别 106 那 1 个独有提交和前端 66 个独有提交价值之前，就用 reset / 强制覆盖类操作追求“SHA 一致”。

⑤ 现在把它当成一道题

你是项目发布负责人。请先不用 Git 命令，只回答：

  1. 为什么 106 的 origin/main = 84382576 和 HEAD = c5e35ae 能同时成立？
  2. 哪些是权威状态？哪些是需要保护的独有历史？哪些只是参考状态？
  3. 最不应该先做的操作是什么类型？为什么？
  4. 设计一个 5 阶段安全收敛流程。
  5. 最后你需要看到哪些可观察证据，才敢说 GitHub、106 checkout 和真实运行服务一致？

⑥ 分级提示

Hint 1 · 方向

先问“哪些信息一旦被覆盖就很难恢复”，再问“怎么同步”。

Hint 2 · 结构

可以把流程想成：盘点 → 保护 → 集成 → 验证 → 发布，而不是“直接 pull”。

Hint 3 · 接近答案

重点检查两类独有历史：106 的 1 个 commit，以及前端分支的 66 个 commits；在它们都被命名、备份、比较之前，不要做破坏性收敛。
