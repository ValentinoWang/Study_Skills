Deep Dive 01 · 约 18–22 分钟

深挖一：一个按钮点击以后，前端到底发生了什么？

如果只说“前端就是 HTML、CSS、JavaScript”，五分钟就能讲完。真正的软件工程入门要继续追问：页面状态是谁维护的？一个点击怎样变成请求？请求失败后页面为什么不能乱？布局为什么会出现多层滚动？

1. 把页面理解成状态函数，而不是截图

现代前端最核心的心智模型可以写成 View = render(props, state)。Props 是外部输入，State 是组件自己维护的当前状态，Render 根据两者产生界面。于是“页面长什么样”只是某个状态下的结果，而不是页面本身。

例如教练正在编辑周计划，至少同时存在三种完全不同的状态：

  • 界面状态：当前选中了周三、动作编辑 Drawer 已打开、某个折叠区展开。
  • 请求状态：保存请求是 idle、loading、success 还是 error。
  • 业务状态：计划是 draft、published、archived，或者当前版本已经被另一个教练修改。

如果把这三类状态混成一个 isPublished，请求一超时就会出现“按钮已经显示发布成功，但数据库并没有确认”的错觉。前端可以做 optimistic UI（乐观更新），但前提是你清楚哪些状态只是临时推测，哪些必须等服务端权威确认。

2. 路由、布局和滚动其实是三件事

Routing 决定“你现在在哪个页面”；Flexbox / Grid 决定“元素怎么分配空间”；Scroll Ownership 决定“内容超出时到底谁滚”。这三件事混起来，页面就容易变成一个不断打补丁的高度系统。

场景更合理的布局意图为什么
设置页、治理页、长表单content / 自然文档流内容多就向下长，让浏览器页面滚动
聊天、地图、IDE、实时工作台fill / 视口填充需要固定工作区，让内部消息区或编辑器滚
统计卡片矩阵Grid二维行列关系比一维 Flex 更清楚
Header + Sidebar + MainFlex / Grid固定区域和剩余空间容易表达

所谓 fill / content 通常是项目自己的布局语义，不是 CSS 官方关键字。判断时先问：这个页面是在“阅读一份会自然增长的内容”，还是在“操作一个需要占满视口的工作台”？

3. 点击“发布”之后是一条跨进程链路

用户点击
→ 前端读取 state
→ 构造 HTTP Request
→ 浏览器发送到网络
→ 反向代理 / API Gateway
→ 后端 Route
→ 身份认证
→ 授权
→ 业务规则
→ Database Transaction
→ HTTP Response
→ 前端更新 request state
→ 再拉取或使用权威业务状态

HTTP Request 常见四部分：Method、URL/Endpoint、Headers、Body。Response 也不只是一个 JSON，还包括 Status Code 和 Headers。初学者最容易犯的错误是把所有非 200 都当成“系统错误”，但从恢复策略看，400 输入错误、401 未认证、403 无权限、409 版本冲突、429 限流、500 服务端错误完全不是一回事。

4. 错误提示的本质是“用户下一步能做什么”

类型例子正确恢复
输入可修复训练日期缺失保留输入，定位字段，告诉用户怎么改
无权限不是该组教练停止提交；不要提供“再试一次”假希望
版本冲突别人已保存 v8拉取新版，比较差异，让用户决定合并
超时不知道服务端是否执行先查询结果或用同一个幂等键安全重试
服务端故障500保留草稿，展示可追踪错误 ID
练习：用户点“发布”后 8 秒没有响应。为什么“直接让他再点一次”可能是危险设计？请分别从前端状态、HTTP 语义和后端副作用三个角度回答。

参考思路：客户端只知道“没收到结果”，并不知道服务端没执行。如果第一次其实已经写库并触发通知，第二次点击会制造重复副作用。因此创建型操作应有稳定业务键/幂等键，前端也要把“结果未知”和“明确失败”分开呈现。
