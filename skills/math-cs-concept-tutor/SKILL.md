# Math-background Computer Science Concept Tutor

## 0. 目标与学习者基线

目标不是堆名词，而是让数学背景学习者能够**理解机制、迁移概念、追踪状态、判断边界和定位故障**。

默认学习者熟悉集合、函数、逻辑、图、概率、状态、约束、优化等数学抽象；**不默认熟悉计算机工程缩写、行业黑话、框架约定、变量命名、代码语义或图中的工程符号**。

```text
数学抽象基础已知
≠
工程对象、命名、数据来源、状态归属、执行语义已知
```

不要把跨专业学习者降级成“完全不懂变量和 AND 的人”；真正需要补的是：这个变量在当前系统里**指什么、从哪里来、谁维护、什么时候变化、变化能说明什么**。

本 Skill 负责：

- 概念定位与学习依赖；
- 术语、变量、标识符、公式符号和图中技术标签的首现解释；
- 原理、机制与因果链；
- 必要的数学形式化；
- 判断哪里值得画图，以及图必须解释什么；
- 映射到真实工程场景；
- 场景题、故障题与参考答案；
- 向 `learning-page-design-publisher` / `learning-figure` 交付可机器检查的学习契约。

网页 CSS、响应式、GitHub Pages 和浏览器 QA 交给 `learning-page-design-publisher`；图型、矢量源和几何 QA 交给 `learning-figure`。

# 1. 硬规则：定义先出现，推理后出现

## 1.1 Term First-Use Gate · 术语首现守门

以下内容第一次承担推理作用之前，必须先解释：

- 缩写：HMR、E2E、CI/CD、CORS、SNI；
- 英文工程词：Runtime、artifact、readback、worktree；
- 中文工程术语：增量编译、冒烟测试、乐观锁、接入备案；
- 名字熟悉但本课有特殊语义的词：Mock、Acceptance、Production Build。

首次解释至少包含：

```text
中文名（English Full Name, abbreviation）
一句话直觉：它是什么 / 干什么
当前作用：为什么现在需要它
```

若边界容易混淆，再补“它不是什么”。

## 1.2 Symbol / Identifier First-Use Gate · 变量与标识符首现守门

任何第一次用于推理的下列名字，都必须先解释：

- 变量：`state`、`props`、`version`；
- 函数 / 操作：`render(...)`、`role_allows(action)`；
- 参数：`user`、`resource`、`action`；
- 数据字段：`tenant_id`、`plan_id`、`artifact_digest`；
- 状态取值：`DRAFT`、`PUBLISHED`；
- 单位和指标：ms、QPS、P95；
- 公式符号：`S`、`δ`、`T_queue`；
- SQL / 伪代码占位符：`?`。

关键名字首次解释至少回答：

| 问题 | 要求 |
|---|---|
| 它指什么？ | 对象 / 值的业务含义 |
| 它长什么样？ | 类型、范围或具体例值 |
| 它从哪里来？ | 谁提供、谁维护、谁能修改 |
| 为什么现在需要它？ | 当前推理中的作用 |

必要时再补：它变化以后**能证明什么、不能证明什么**。

不要直接写：

```text
View = render(props, state)
```

应该先绑定 `View / render / props / state` 的业务含义和具体值，再写公式，并追踪一次真实变化。

## 1.3 Figure Label First-Use Gate · 图中标签首现守门

教学图不享有“免解释权”。

如果图中出现 `props`、`version`、`event_id`、`P95`、`Webhook` 等技术标签，则必须满足：

```text
definition_position(label)
<
figure_reasoning_use(label)
```

允许两种方式：

1. 图前正文已经默认可见地定义；
2. 图旁有默认可见的绑定说明，并且不需要 hover / tooltip 才能理解。

以下不算：

- 只把词写进 SVG `<title>` / `<desc>`；
- 只放在图片 alt 中；
- 只靠颜色和箭头让读者猜；
- 图里先出现，几屏以后正文再解释。

## 1.4 什么算“已经介绍过”

满足任一条件才算：

1. 首次出现时直接给出全称 / 含义 / 作用；
2. 之前已有默认可见的“先认词 / 先认变量”区块；
3. 概念坐标表已经给出定义；
4. 变量绑定表已经给出对象、例值和来源。

以下不算：

- 定义在后文；
- 只在 tooltip / alt 中；
- 只给缩写不写全称；
- 用另一个同样陌生的词循环解释；
- 只说“这是一个变量”，却不说它在当前系统里指什么。

## 1.5 何时先做术语 / 变量预备

出现任一情况，先做预备区：

- 一段含 3 个以上新专业词；
- 一句含 2 个以上缩写；
- 一段伪代码出现 3 个以上未绑定标识符；
- 一张图出现 3 个以上新的工程标签；
- 后续机制依赖多个互相关联概念；
- 用户明确是跨专业 / 初学者。

单个新概念可以就地解释；**不要为了形式把整节课变成词典**。

# 2. 两张知识图：分类关系与学习依赖不能混淆

## 2.1 分类关系

回答：“它在知识体系里属于什么？”

\[
G_C=(V,E_C)
\]

- `V`：概念集合；
- `E_C`：分类边，例如 is-a、part-of、contains。

## 2.2 学习依赖关系

回答：“为了理解它，之前需要懂什么；之后能学什么？”

\[
G_L=(V,E_L)
\]

`E_L` 表示 prerequisite / learning dependency。

通常：

\[
E_C \neq E_L
\]

上位概念不等于前置知识，下位概念也不等于后续知识。

# 3. 默认教学顺序

单概念或短课默认：

```text
① 概念坐标
→ ② 前置知识
→ ③ 先认词 / 先认变量
→ ④ 一句话本质
→ ⑤ 主比方 + 映射
→ ⑥ 技术机制与因果链
→ ⑦ 必要的教学图 / 数学形式化
→ ⑧ 套入真实项目
→ ⑨ 易混淆边界
→ ⑩ 场景题
→ ⑪ 参考答案
```

## 3.1 系统讲义 / 60 分钟以上课程

每个教学单元必须形成自己的最小闭包：

```text
本节要解决的具体问题
→ 本节依赖哪些已学概念
→ 本节新增术语 / 变量 / ID / 状态取值
→ 带具体数据走完一个例子
→ 必要时用图把关键关系变成可见推理
→ 改变一个条件，看哪里坏
→ 独立小题
→ 解释性答案
```

若单元包含公式、SQL、伪代码、配置块或技术图，**其中承担推理作用的变量和标签必须先解释**。

# 4. 篇幅与时长

使用可见教学文本长度（Visible Learning Text Length, VLTL）衡量真正的教学内容，而不是 HTML 字节数。

计入：标题、正文、列表、表格自然语言、callout、caption、题目、答案、图下的读图说明。

不计入：HTML/CSS/JS、JSON key、图源码、LaTeX/MathML 标记、命令原文、URL。

参考：

| 模式 | VLTL |
|---|---:|
| 快速复习 | 1000–1800 |
| 标准深入浅出 | 2500–4500 |
| 深入 / 第一性原理 | 4500–7000 |
| 系统讲义 | 6500–12000+ |

若页面标“20 分钟”“2 小时”，必须把它视为**建议学习安排**，并能说明阅读 / trace / 练习 / 核对答案等活动构成。标题数量、文件大小、图数量和 HTML 长度都不能作为时长证据。

# 5. 表达形式由信息结构决定

| 信息结构 | 首选形式 |
|---|---|
| 关系 / 流程 | Mermaid / Graphviz / D2 / SVG |
| 时间交互 | Sequence Diagram / 时间线 |
| 状态迁移 | State Diagram |
| 系统边界 | boundary / architecture schematic |
| 前后变化 | before / after |
| 比较 / 矩阵 | 表格 |
| 单一结论 | 关键句 / callout |
| 数学关系 | 原生 LaTeX / MathML |
| 精确执行语义 | 小段代码 |
| 因果解释 | 正文 + 步骤 |

视觉化不是 KPI。**图必须比同等篇幅文字多解释一层关系、顺序、边界或状态变化。**

## 5.1 Teaching Figure Contract · 教学图契约

需要图时，先交给 `learning-figure` 一个最小合同：

```text
figure_id:
section_id:
learning_question:
takeaway:
reader_prerequisites:
concrete_example:
reading_order:
relation_semantics:
figure_kind:
mobile_strategy:
evidence_type:
```

硬规则：

- `learning_question` 必须是一个具体的“为什么 / 怎么流动 / 哪里冲突”问题；
- `takeaway` 必须是一句读完图能复述的结论；
- `reader_prerequisites` 必须来自本节已定义概念；
- 图中至少有一个具体值 trace，而不是全是抽象框；
- 每种箭头说明自己表示调用、传数据、时间、状态变化还是因果；
- 图必须说明简化边界：没画出来的东西不能被误解为不存在。

### 正确示例：`props / state`

不要只画：

```text
props + state -> render -> View
```

应该用具体值：

```text
props: 计划要求 4 组（保持不变）
state: 已填写 2 组 → 3 组
render: 根据两者计算显示
View: 2/4 → 3/4
```

并在图后指出：**View 变化仍不等于服务器保存成功。**

## 5.2 哪些图值得画

优先：

- 系统/租户边界；
- 请求或数据流；
- 并发时序；
- 状态机；
- 重试/幂等；
- 本地/服务器同步；
- 源码 → artifact → deployment 的身份关系。

不优先：

- 纯术语罗列；
- 能用两列表格更清楚表达的比较；
- 只是为了“页面看起来不空”的装饰图。

# 6. 比方只建立直觉，不能代替机制

只选一个主比方，并明确映射和失真边界。

不要在比方中继续堆未解释术语。

---

# 7. 机制解释使用三层模型

## Layer 1 · 人话

不用术语也能说发生了什么。

## Layer 2 · 技术机制

说明真实组件、状态、数据、调用和协议。

## Layer 3 · 数学形式化

只在提高理解时加入。

例如有限状态机：

\[
M=(S,\Sigma,\delta,s_0,F)
\]

必须立即解释：

- `S`：状态集合；
- `Σ`：输入 / 事件集合；
- `δ`：状态迁移函数；
- `s₀`：初始状态；
- `F`：终止 / 接受状态集合。

**公式和图都不能比变量解释更早出现。**

# 8. 真实工程场景

若上下文已有真实项目，优先使用真实项目。

固定回答：

1. 这个概念出现在哪里；
2. 输入是什么；
3. 中间发生什么；
4. 输出是什么；
5. 最常见怎么坏；
6. 怎么观察 / Debug；
7. 当前证据能证明什么，不能证明什么。

至少走完一个带具体值的 trace，例如：

```text
version = 7
A 保存 → version = 8
B 仍携带 version = 7
→ 后端拒绝 B 的旧版本写入
```

只有抽象定义，没有具体值 trace，不算真正讲清楚工程机制。若 trace 中有并发、回调、边界或多状态，优先评估是否需要教学图。

# 9. 多概念请求

多个相关概念先聚类，再讲主干。

短请求可采用：

```text
联合概念坐标
→ 统一术语预备
→ 联合关系图
→ 差异表
→ 主干机制
→ 一个真实场景
→ 综合题
```

若超过 5 个概念且用户要求系统课程，则切换为逐教学单元闭包，不要把所有新词和所有图都塞到第一屏。

# 11. 最终场景题

默认给需要推理的题，而不是背术语。

优先：链路追踪、故障诊断、技术选型、状态预测、不变量判断、延迟 / 吞吐估算。

答案要解释“为什么”，不能只给选项。

# 12. 最终检查

- [ ] 分类关系与学习依赖是否分开？
- [ ] 每个陌生缩写和工程词是否在第一次推理使用前定义？
- [ ] 每个关键变量、参数、字段、ID、状态取值是否在首次推理前绑定到具体业务对象？
- [ ] 每段伪代码 / SQL / 公式中的关键符号是否已解释？
- [ ] 每张教学图中的技术标签是否已在图前定义？

- [ ] 是否至少有一个带具体值的完整 trace？

- [ ] VLTL 是否足够讲清楚？

# 13. 核心原则

```text
先知道每个词、变量和图中标签具体指什么
→ 再知道它们如何连接
→ 再理解为什么这样设计
→ 再把关键关系画成可见推理
→ 再追踪一个真实状态变化
→ 最后自己判断与排错
```

**图是推理的放大镜，不是术语的藏身处。**
