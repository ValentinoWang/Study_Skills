Orient

① 这段材料到底在说什么

一句话：你真正要优化的不是“能不能彻底不编译”，而是每次小改是否只做与改动规模相匹配的最小反馈。把日常开发和发布证明混成一条流水线，才是“改一个按钮也要等 Docker”的根因。

核心判断：开发态应该优先复用已经运行的 Runtime，用 HMR / Hot Reload / 增量编译只更新受影响部分；Mock、真实 API 联调和目标平台验证逐级增加真实性；Production Build、Docker、全量 E2E 和线上 readback 留到合并或发布节点。

事实 · Docker 解决什么

Docker 的核心价值是封装运行环境和交付一致性。它非常适合后端、依赖复杂服务和生产部署，但它不是“看一眼前端按钮颜色”的必要前置。

推断 · 真正要缩短什么

应该缩短的是 修改 → 看见效果 → 判断对错 的反馈回路，而不是为了追求“零编译”把目标平台验证也删掉。

风险 · 快速检查不能冒充发布证据

Mock 成功、H5 正常或 Chrome 正常，都不能证明微信 Runtime、原生插件、生产构建和线上部署一定正常。快路径与发布门禁必须明确分层。

把开发想成数学研究：日常改动像先做数值实验和局部引理；只有准备提交“正式证明”时，才跑完整构建、全量测试、容器和部署读回。每改一个符号都重写整篇证明，当然会慢。

Learn

② 你必须先认识的概念

这组术语决定你是否能正确拆分流水线。每张卡都要回答：它是什么、解决什么、在本课案例里何时出现。

Development Feedback Loop · 开发反馈循环
直觉
改完代码之后，你多久能看到结果并判断“这次改动对不对”。
严格一点
它包含源码变化、必要转换/编译、运行时更新、数据准备、测试与人工观察等环节；优化目标是减少与当前改动无关的工作。
当前案例
MathArc、Sub2API、uni-app、Flutter、小程序虽然工具不同，但都应该把日常反馈循环与发布流水线拆开。
HMR / Hot Reload · 热更新
直觉
应用已经跑着，只把刚改的那部分代码塞进去，让界面快速变化。
严格一点
Vite HMR 通常以模块为单位更新；Flutter Hot Reload 把变化后的 Dart 代码注入运行中的调试 Runtime 并重建 Widget Tree。它们都不是 Production Build。
当前案例
Sub2API 的 Vite、uni-app H5 和 Flutter Debug Runtime 都可以承担日常 UI/业务逻辑反馈。
Incremental Compilation · 增量编译
直觉
不是把整座房子重建，只重做你刚改动影响到的那几块。
严格一点
编译器根据依赖关系重处理变化单元及其受影响依赖，而不是每轮重新生成完整发布产物。
当前案例
uni-app、Flutter、小程序开发态可能仍然存在“编译/转换”，但这与全量 release build 是两件事；你真正应该避免的是不必要的全量重构建。
Mock API · 模拟接口
直觉
后端还没准备好，先让一个“假后端”稳定返回你需要的各种状态。
严格一点
Mock 用确定性的 fixture 或契约生成响应，让前端独立验证 success、empty、loading、403、409、500 等状态。
当前案例
UI 开发和错误态验证优先用 Mock；它可以减少对真实服务器、数据库、支付和账号状态的依赖，但不能算真实后端验收。
API Proxy · 接口代理
直觉
浏览器只访问本地开发服务器，本地服务器再帮你把 /api 转发到已有后端。
严格一点
开发服务器作为反向代理统一请求来源，可处理开发态跨域与后端目标切换；目标可以是本地、测试或受控远端环境。
当前案例
Sub2API 和 uni-app H5 都适合用 dev server proxy 连接已有 API，从而做到“不重建前端，也能联调真实接口”。
Target Runtime · 目标平台运行时
直觉
浏览器里看起来对，不代表微信、Android 或 iOS 里也一定对；最终还要去真正的平台环境检查。
严格一点
目标 Runtime 提供平台自己的生命周期、系统 API、渲染差异、权限和原生插件行为，是跨端正确性的必要证据层。
当前案例
wx.login、微信支付、相机、蓝牙、Flutter native plugin 等不能只靠 H5/Chrome 证明，需要进入微信开发者工具、模拟器或真机。
Production Build · 生产构建
直觉
这是准备交付给用户的正式产物，不是给开发者快速试错的草稿。
严格一点
Production Build 会执行面向发布的优化、资源输出、平台打包或可部署产物生成；它验证的是“能否被正式交付”。
当前案例
npm run build:mp-weixin、flutter build ...、Vite production build、Go embed 等应放在合并/发布证明，而不是普通样式修改循环。
Docker Build · 容器镜像构建
直觉
把程序和依赖装进一个标准运输箱，保证服务器拿到的是同一套运行环境。
严格一点
Docker build 根据 Dockerfile 组装镜像层，常包含依赖安装、生产构建、二进制编译和镜像导出，因此通常比前端开发服务器重得多。
当前案例
Sub2API 发布时需要 Docker 很合理，但只改前端文案时没必要重做镜像；uni-app / Flutter / 小程序前端日常开发通常也不需要 Docker。
Connect

③ 概念关系与最小知识闭包

把所有技术栈统一成五级反馈模型。越往右，运行环境越接近真实发布，成本和证明强度也一起上升。

最小知识闭包：优化的是 Δ，不是整个仓库 N

把一次反馈时间粗略写成：

Tfeedback, full=Tinstall+Tfull-build(N)+Tdocker+Tfull-test(N)

而日常快速反馈更希望接近：

Tfeedback, fast≈Tincremental(Δ)+Taffected-test(A(Δ))
因此“无 Docker”不等于“零编译”。 uni-app、Flutter、小程序开发态仍可能做源码转换或增量编译；只要它复用 Runtime、只处理变化范围，它依然属于快路径。真正重的是每次都生成完整发布产物、完整容器、完整截图矩阵和完整 E2E。
级别你在证明什么典型工具什么时候停在这里就够了
L0布局、文案、基础交互Vite、http.server、Widget Preview / Chrome纯 UI/CSS/文案改动
L1前端状态机在固定数据下正确MSW、fixtures、Fake Repository、契约 Mock接口未完成、异常态和空态开发
L2前后端契约与真实请求正确dev proxy、测试后端、API smoke请求映射、权限、SSE、错误码
L3目标平台能力正确微信开发者工具、模拟器、真机平台 API、权限、原生插件、生命周期
L4正式交付链条正确Production Build、CI、Docker、上传/部署 readback提交、合并、发布候选、生产上线
Reconstruct

④ 把真实案例重新还原

把你前面遇到的三类项目放进同一个模型，会发现它们只是“最低可用 Runtime”不同。

案例 A · MathArc：静态前端 + Python Runtime

L0：纯 HTML/CSS/JS 页面可以直接由静态服务器提供，几乎没有前端编译成本。

python3 -m http.server 4173 --directory docs/prototypes

L1：用确定性的 demo server 返回固定 Agent 过程；L2：切到真实 workspace API；只有正式验收才跑完整浏览器门禁和发布流程。

这类项目说明：如果源代码本身就是浏览器可执行格式，“零前端编译”是真正可实现的。

案例 B · Sub2API：Vite 前端 + Go 后端 + Docker

L0/L1：Vite dev server + HMR 看页面或接 Mock；L2：dev server 通过 Proxy 接已经运行的本地/测试后端。

只改页面、样式和文案时，不需要重新编译 Go。修改后端逻辑时才重新构建后端；正式交付时再把前端 production build、Go 二进制、Docker 镜像与线上 readback 串起来。

生产后端代理的边界：如果为了方便把本地前端代理到生产 API，应默认只做安全读取；登录、支付、删除、配置修改等写操作不能当普通 UI 调试随意执行。

案例 C · AthleteOS 类跨端客户端

当客户端是 uni-app、Flutter 或原生小程序时，开发态不能简单理解成“完全不编译”，因为源码需要进入各自 Runtime。

正确做法是：先在最轻 Runtime 里完成大多数 UI/业务逻辑，再在涉及平台 API 时升级到 L3。例如 uni-app 先 H5，Flutter 先 Chrome，原生小程序直接在微信开发者工具中增量调试。

目标不是删除平台验证，而是让平台验证只在真的受平台差异影响时发生。

事实

uni-app CLI 把 dev:h5/dev:mp-weixin 与 build:h5/build:mp-weixin 分开；Flutter 也区分 flutter run 调试周期与 flutter build 发布构建。

推断

因此你的统一工程规范不应该写成“所有前端都不编译”，而应该写成“默认使用开发态 Runtime 与增量反馈，不执行发布级全量构建”。

风险

H5/Chrome 只是快速近似环境。平台组件、生命周期、权限、原生插件、微信 API 等一旦进入改动范围，必须升级到 L3。

现在把三种跨端方案放到“最快反馈 → 真实联调 → 平台验证 → 发布”的同一张表里。

给 AI / Vibe Coding 工作流一个统一入口

不要让 Agent 记住每个仓库几十条命令。给不同技术栈暴露同样的四个语义入口：

make preview       # 最快看 UI / 基础交互
make mock          # 固定接口状态，独立开发前端
make integration   # 连接真实测试 API / 目标开发服务
make verify        # 发布级完整证明：build / tests / Docker / readback（按项目需要）

Hint → Answer

⑦ 分级提示，最后就是实际答案

Hint 1 · 方向

先不要看技术栈名称，只问一个问题：这次改动改变了哪一层的行为？ UI → L0；固定状态 → L1；真实接口 → L2；平台 API → L3；构建/部署链 → L4。

Hint 2 · 结构

Mock 与真实 API 不是二选一：Mock 适合把 success/409/500 等状态固定下来做前端逻辑；真实测试 API 用来证明契约、序列化、权限和网络路径真的一致。平台 API 则必须再升级到目标 Runtime。

Hint 3 · 接近答案

改动最低层级关键理由
A UI 文案L0不涉及接口和平台
B API 枚举/409L1 → L2先固定状态，再真实联调
C wx.login / native pluginL3必须目标 Runtime
D Dockerfile / Go embedL4改的是交付链本身
E 正式上线L4必须形成发布证明

答案 · 实际答案

A：L0。 用 Vite/H5/Chrome/开发者工具的最快开发态预览即可；不需要 Production Build，更不需要 Docker。若只是视觉与文字变化，跑一次相关页面 smoke 就足够。

B：L1 → L2。 先用 Mock 固定新枚举、409、空状态等，让前端状态机可重复验证；随后用真实测试 API 做窄联调，确认实际响应字段、状态码和权限一致。仍然不需要 Docker，除非后端交付物本身也被修改。

C：L3。 uni-app 的 H5 或 Flutter Chrome 可以继续帮助开发普通 UI，但不能作为最终证据。wx.login 要进入微信 Runtime；相机原生插件要进入 Android/iOS 模拟器或真机。这里仍然通常不需要 Production Build，只需要目标平台的开发态 Runtime。

D：L4。 因为你修改的不是页面，而是 Production Build / Go embed / Docker 交付路径本身。Vite 只能证明开发态页面，无法证明镜像内资源、二进制嵌入和服务器启动后的实际读回。这次必须构建真正的发布候选并验证。

E：L4。 L0–L3 的结果可以作为前置证据并帮助快速定位问题，但正式上线仍要执行项目规定的 production build、必要的全量/关键 E2E、Docker 或平台打包、部署/上传与最终 smoke/readback。

可以迁移到所有项目的一句话：日常开发选择“足以证明当前改动”的最低反馈层；提交、合并与发布节点再升级到完整发布证明。这样既不牺牲严谨性，也不会让每次小改都支付整个仓库的构建成本。
