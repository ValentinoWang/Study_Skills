Primer

① 先把后文会反复出现的词认清楚

先认词：先读每张卡片标题下的一句话直觉；需要严格定义、边界或案例作用时再展开。后文不会默认你已经认识这些工程缩写。
Object Database：blob / tree / commit
直觉
Git 的核心不是“保存很多文件夹副本”，而是保存不可变对象，并用哈希把对象连接起来。
严格定义
blob 保存文件内容；tree 保存目录结构和文件名到对象的映射；commit 指向一个根 tree、零个或多个父 commit，并携带作者、提交者和消息等元数据。对象通过内容寻址，被 SHA-1/SHA-256 形式的对象 ID 标识（具体仓库格式取决于 Git 配置）。
比喻
像数学里的不可变节点图：commit 是节点，父指针是有向边；分支名只是给某个节点贴的可移动标签。
边界
分支名不是提交内容本身；删除一个 branch ref 也不一定立即删除 commit 对象。反过来，工作区里看到的文件也不是 Git 历史本身。
本案作用
理解对象不可变之后，就容易看懂：main、origin/main、HEAD 只是指向对象图某处的可移动引用。
Reference（ref）与 Branch
直觉
branch 本质上是一个会移动的名字，它通常指向某个 commit。
严格定义
本地分支一般存于 refs/heads/*；tag、remote-tracking ref 等属于其他引用命名空间。创建新 commit 时，当前分支 ref 会移动到新 commit。
比喻
像书签：书签名字可以叫 main，但不同人的书里同名书签完全可能夹在不同页。
边界
“分支包含哪些文件”是口语简化。严格地说，分支指向一个 commit，commit 再指向快照。两个分支可以指向同一 commit，也可以后来发生分叉。
本案作用
比较本地 main、GitHub main 和服务器分支时，不要把名字相同当作对象相同，最终要比较它们各自解析到的 commit ID。
HEAD 与 Detached HEAD
直觉
HEAD 表示“当前这个工作目录站在哪里”。通常它指向一个本地分支，也可以直接指向某个 commit。
严格定义
HEAD 常常是 symbolic ref，例如指向 refs/heads/main。detached HEAD 时，HEAD 直接指向 commit；这时新提交仍会产生对象，但没有普通分支名自动跟随它们。
比喻
像你当前打开的书页：别人把目录索引更新了，不会自动把你手里的书翻到那一页。
边界
HEAD 不等于 origin/main，也不等于服务器正在运行的容器镜像。Git 工作目录当前 commit 与实际生产进程版本仍需单独核验。
本案作用
服务器上 origin/main 已 fetch 到新 SHA，但 HEAD 仍在旧分支时，工作树不会因为 fetch 自动切到新代码。
Index / Staging Area
直觉
Git 在工作区和 commit 之间还有一层“下一次准备提交什么”的索引。
严格定义
index 保存下一次 commit 快照的候选状态。git add 把工作区内容写入对象库并更新 index；git commit 基于 index 创建新的 tree/commit。
比喻
像交作业：工作区是草稿纸，index 是你放进提交袋里的版本，commit 是正式封存。
边界
工作区 clean 需要同时考虑“index 相对 HEAD 无 staged 变化”和“working tree 相对 index 无 unstaged 变化”。只看有没有未跟踪文件或只看 diff 一种方向都可能漏信息。
本案作用
当你说服务器“工作树干净”，严格含义只是本地未提交状态干净，不能推出分支最新、远端同步、生产部署正确。
Working Tree 与 clean / dirty
直觉
working tree 是你在磁盘上实际编辑的文件；它可以和 HEAD、index 不同。
严格定义
git status 通过比较 HEAD↔index、index↔working tree，再结合 untracked 文件来呈现未提交状态。clean 通常意味着没有待提交、待暂存的已跟踪变化以及需要提示的未跟踪变化。
比喻
像桌面收拾得很整齐，不代表你桌上的教材是最新版。
边界
clean 只描述“相对当前 HEAD 的本地修改状态”，完全不回答 HEAD 是否落后远端、是否在错误分支、是否对应部署中的进程。
本案作用
106 服务器 clean 但 HEAD 在旧 commit 时，结论应该是“旧版本被干净地检出”，不是“服务器已经同步最新版”。
Remote-tracking ref：origin/main
直觉
它是本地对“上次 fetch 时远端 main 在哪里”的记录，不是远端本身，也不是当前 checkout。
严格定义
refs/remotes/origin/main 通常由 git fetch origin 更新。它用于比较和作为新分支基线；普通开发不直接在这个 ref 上提交。
比喻
像本地缓存的一份列车时刻表：fetch 是刷新时刻表，checkout/switch 才是你真正换乘。
边界
如果很久没 fetch，origin/main 可能陈旧；如果刚 fetch，它可以准确反映远端当时状态，但 HEAD 仍然不会自动移动。
本案作用
服务器 origin/main = GitHub main 只能证明“服务器知道远端最新位置”，不能证明服务器实际文件或运行进程已更新。
Commit DAG、Ancestor 与 Reachability
直觉
Git 历史是有向无环图，不是一条“最新到最旧”的单线时间轴。
严格定义
commit 指向父 commit，因此从某个 commit 沿父边可到达的集合就是它的祖先历史。若 A 可沿父边到达 B，则 B 是 A 的 ancestor。merge commit 可有两个或更多父。
比喻
像偏序集：祖先关系给出偏序，不是所有 commit 都能比较出“谁包含谁”。
边界
提交时间不决定祖先关系。一个较晚创建的 commit 可以基于较旧分支，与另一条历史互不为祖先。
本案作用
判断能否 fast-forward、哪些提交只存在一侧、是否真正分叉，都应该基于 DAG 可达性而不是时间戳或 SHA 大小。
Merge Base 与 ahead / behind
直觉
比较两条分支时，先找到共同祖先，再数双方各自独有的可达提交。
严格定义
git merge-base A B 找最佳共同祖先；A...B 表示对称差历史，常配合 git rev-list --left-right --count A...B 统计双方独有提交数。
比喻
像集合论：从共同祖先开始，计算两边的集合差，而不是比较两个集合最后一个元素的时间。
边界
ahead/behind 是相对于某一对 refs 的计数，不是仓库的全局属性，也不表示代码质量、时间新旧或文件变化量。不同比较对出现 631/1 和 621/66 完全不矛盾。
本案作用
案例里应该分别写清“GitHub main vs 106 HEAD”和“GitHub main vs 本地前端分支”，不能把两个数字拼成一个故事。
Fast-forward、Merge、Rebase、Cherry-pick
直觉
这些操作都能“把改动带到另一条历史”，但它们改变图的方式不同。
严格定义
fast-forward 只是移动 ref，不创建 merge commit；merge 把两条历史通过新 merge commit 汇合；rebase 重新复制一串 commit 到新基线上，产生新的 commit IDs；cherry-pick 把选定提交的补丁语义应用到当前基线并创建新 commit。
比喻
像证明重组：merge 保留两条推导路径并在末端合流；rebase 是把一串推导重新建立在新公理基线上。
边界
已经共享的公共历史随意 rebase 会改变 commit identity，可能给协作者造成重复和冲突；merge 也不是永远优于 rebase。选择依据是历史协作语义，而不是“哪个命令更高级”。
本案作用
把前端 66 个独有提交合入最新 main，可以选择 merge 或有计划地重放；服务器 1 个独有热修若仍有价值，可能更适合单独 cherry-pick。
reset / restore / revert
直觉
这三个命令名字都像“撤销”，但作用对象和历史语义完全不同。
严格定义
git reset 主要移动当前分支/HEAD，并可同时改变 index 和 working tree；git restore 针对工作区/index 内容恢复；git revert 新建一个反向提交来抵消已有 commit 的效果。
比喻
像改账本：reset 是把“当前指针”挪回旧页并可撕掉草稿；revert 是在新页记一笔相反分录。
边界
reset --hard 会丢弃当前 index/working tree 的修改，并可能把分支移走；对尚未保护的独有历史非常危险。revert 不重写已有共享历史，但可能产生冲突。
本案作用
在 106 独有提交尚未建 backup ref 前，不应把 hard reset 当“同步服务器”的第一步。
worktree、stash 与可恢复引用
直觉
一个仓库可以同时有多个工作目录；stash 也能临时保存工作区/index 状态，但它们都不是“自动合并来源”。
严格定义
git worktree 允许同一仓库对象库挂载多个工作目录，每个 worktree 有自己的 HEAD/index；stash 记录工作区/index 的临时快照。两者都需要显式检查，不能因为主 worktree clean 就假设别处无工作。
比喻
像同一本资料库开了多个实验台：主实验台整理好，不代表隔壁实验台没有唯一样品。
边界
删除 worktree、清理 stash 或回收不可达对象前，应确认是否存在唯一数据。reflog 提供一定恢复机会，但恢复能力不是数据治理方案。
本案作用
当仓库存在服务器临时 worktree、历史 stash 或 Agent 生成分支时，收敛前先做 inventory，确定哪些是 refs、哪些是未提交状态、哪些只是缓存。
部署版本 ≠ Git checkout 版本
直觉
服务器目录里的 HEAD 只是源码状态，真正对外服务的进程、二进制或镜像可能来自另一个 commit。
严格定义
部署通常还包含 build artifact、容器镜像、systemd 进程、环境变量和数据库 schema。可靠发布应能把运行版本映射回 source commit，例如注入 Git SHA、镜像 digest 或 build metadata。
比喻
像源码是菜谱，正在端上桌的菜是构建产物；你换了菜谱，不代表厨房里那锅菜自动重做。
边界
即使 HEAD = origin/main，如果旧 Docker 容器没有重建/重启，对外服务仍可能运行旧代码；反过来，工作目录被改动也不一定改变正在运行的二进制。
本案作用
案例最终验收不能只看三个 SHA 相等，还要验证生产进程/镜像可追溯到同一个发布 commit 并通过 health/smoke。
Orient

② 这段材料到底在说什么

一句话：Git 的“状态不一致”不是一个 bug，而是它允许多个引用、多个工作区和多个历史分支独立演化的直接结果。真正的问题是：你有没有把每个状态变量说清楚。

把 Git 仓库抽象成四元组：S = (G, R, I, W)。其中 G 是不可变对象组成的提交图，R 是 branches/tags/remote-tracking refs 等可移动引用，I 是 index，W 是 working tree。大多数 Git 困惑都来自把这四个东西混成“代码版本”。

例如，“服务器已经 fetch 最新 main”只改变了 R 里的 origin/main；它不会自动移动当前 HEAD，不会自动改 index/working tree，更不会自动重建 Docker 镜像或重启生产进程。于是完全可能同时出现：

GitHub main       = 84382576
server origin/main= 84382576   # 服务器已经知道远端在哪
server HEAD       = c5e35ae    # 服务器实际 checkout 仍在别处
working tree      = clean      # 但相对 c5e35ae 没有未提交改动
runtime image     = ???        # 还需要单独证明

第一层：对象与历史

commit 不会因为分支移动而“变成另一个 commit”。先保护独有对象，再考虑把引用收敛。

第二层：引用关系

main、origin/main、HEAD 都只是名字/指针。比较它们必须解析到具体 commit，并检查祖先/可达关系。

第三层：未提交状态

index、working tree、untracked、stash、worktree 可能保存唯一内容；hard reset 之前必须先盘点。

clean 的严格含义为什么很窄

简化地说，如果把当前 HEAD 快照记作 T_H、index 快照记作 T_I、工作区可跟踪内容记作 T_W，那么“没有 staged/unstaged 修改”要求它们在相关比较上相等：

TH=TI=TW

但这个等式里根本没有 origin/main。所以 clean 与 up-to-date 是两个正交命题：一个回答“有没有本地未提交变化”，另一个回答“当前 commit 与某个远端 ref 的图关系是什么”。

工程目标：不要追求“所有 SHA 越快一样越好”。收敛顺序应该是：先知道独有数据在哪里 → 建立可恢复引用 → 在非生产分支集成 → 验证 → 更新权威 main → 最后部署并证明运行版本。
Connect

③ 概念关系与最小知识闭包

blob / tree / commit→ Commit DAG→ refs / branch→ HEAD→ index→ working tree
remote GitHub main→ git fetch→ origin/main→ merge / rebase / ff→ local main / HEAD→ build / deploy→ runtime artifact
两个图同时存在：上面第一行是 Git 内部数据模型；第二行是协作/交付数据流。理解第一行能解释命令语义，理解第二行能避免把“fetch 了”误解成“服务器已经发布”。

最小知识闭包 1：分支关系是偏序，不是时间排序

设提交图为 DAG G=(V,E)，边从子 commit 指向父 commit。定义 B ≼ A 表示从 A 沿父边可以到达 B，也就是 B 是 A 的 ancestor。这个关系是偏序：有些 A、B 互不为祖先，它们发生了真正分叉。

因此“哪个 commit 时间更晚”不能替代“哪个包含哪个”。fast-forward 是否可能，只取决于祖先关系：如果当前 commit 是目标 commit 的 ancestor，就可以只移动 ref；否则需要 merge、rebase、cherry-pick 或其他显式集成。

最小知识闭包 2：ahead / behind 的数学含义

给定两个 tips A、B 和共同基线 M，粗略可以理解：

ahead(A,B)=|Reach(A)∖Reach(B)|

behind(A,B)=|Reach(B)∖Reach(A)|

git merge-base A B
git rev-list --left-right --count A...B
git log --oneline --left-right A...B

所以“server 比 GitHub behind 631、ahead 1”和“frontend 比 GitHub behind 621、ahead 66”描述的是两组不同集合差，完全可以同时成立。

最小知识闭包 3：fetch、pull、switch、merge 分别改变什么

操作主要改变 refsindex / working tree历史图关键风险
git fetch更新 remote-tracking refs，如 origin/main通常不改当前工作区下载对象但不重写本地分支低；但 fetch 后仍要理解分叉
git switch branch改变 HEAD 指向检出目标分支快照不创建新历史未提交变化可能阻止或被带过去
git merge B成功后移动当前分支更新到合并结果可能新建 merge commit冲突需要逐项解决
git rebase B当前分支最终指向新复制 commits随过程更新重写 commit IDs共享历史需要谨慎
git reset --hard X移动当前分支/HEAD强制改 index 与 working tree旧 commit 可能变为仅 reflog 可达高：未保护数据可丢
git revert X新增 commit 后移动当前分支更新为反向变更结果不删除原历史语义冲突但共享历史更安全

最小知识闭包 4：为什么 reflog 不是备份策略

reflog 记录本地 ref/HEAD 曾经指向哪里，很多误操作后确实能用于恢复。但 reflog 有保留期限、是本地性的，也可能在垃圾回收后失去对象。成熟流程应该在危险操作前主动建立明确 branch/tag 或远端备份 ref，而不是事后祈祷 reflog 还在。

git branch backup/server-20260831 c5e35ae
git branch backup/frontend-20260831 a0580dec
git show --stat backup/server-20260831
git log --oneline origin/main..backup/server-20260831

最小知识闭包 5：冲突数量不是“谁对谁错”

48 个冲突文件只说明 Git 无法自动合并那些路径/片段。它既不证明前端分支错误，也不证明 main 应该被覆盖。冲突解决是一个语义判断：在最新 main 的架构约束上，哪些旧改动仍代表你真正想保留的行为？

批量 ours/theirs 的危险：它把“解决冲突”退化成“选一边覆盖”，会丢失另一边非冲突但仍相关的语义。正确做法是先理解双方变化，再逐功能验证。

最小知识闭包 6：Git 收敛和生产收敛是两件事

设最终权威 commit 为 M。Git 收敛可以要求 local main = origin/main = GitHub main = M；但生产收敛还要增加 runtime_source = M 或至少可验证的 artifact digest → M 映射。否则你会得到“仓库看起来全对，线上仍旧”的假阳性。

最小知识闭包 7：三方合并为什么需要 merge base

Git 合并不是简单比较 A 和 B 两份最终文件，然后决定谁覆盖谁。典型三方合并会同时看共同祖先 M、当前分支 A、待合并分支 B：分别计算 M→A 与 M→B 的变化，再尝试组合。只有两边对同一语义区域做了无法自动协调的修改时，才产生冲突。

这解释了一个重要现象：两个分支最终文件看起来差异巨大，也不一定产生很多冲突；反过来，即使只改了少量行，只要双方碰到同一上下文，也可能冲突。冲突数量因此不能直接当“分支质量分数”。

最小知识闭包 8：commit identity 和 patch identity 不是一回事

rebase、cherry-pick 会创建新的 commit，即使代码变化“看起来一样”，commit ID 也通常不同，因为父提交、元数据等发生变化。因此判断“这个修复是否已经以等价补丁进入 main”有时不能只用 SHA 相等，还需要看 patch、文件 diff、测试和功能证据。

这也是为什么大规模历史整理后，旧分支可能显示很多“独有 commits”，但其中部分语义已经以新 commit 形式进入主线。此时不能机械地把所有旧 commit 再 cherry-pick 一遍，否则可能重复应用同一修改。

最小知识闭包 9：删除 branch 为什么不等于删除历史

branch 只是 ref。删除 branch 主要删除一个名字；只要其 commit 仍被其他 refs、reflog 或对象可达关系引用，历史对象仍可能存在。但如果某一串 commit 只有这个 ref 能稳定到达，删除后就降低了可发现性和可恢复性，未来垃圾回收也可能清理不可达对象。

所以“这个分支看起来没用了”不是删除依据。先用 git branch --merged、git log main..branch、比较 patch/功能证据确认没有独有价值，再做清理。

第一问：服务器到底“同步了没有”？

答案必须拆成三句话：服务器的 origin/main 已同步到远端观察结果；服务器的当前 HEAD 没有同步到 main；实际运行服务版本未知，需要继续查构建/容器/进程。只说“同步了”或“没同步”都过于粗糙。

第二问：为什么不能先在 106 上 reset --hard？

因为服务器有一个独有 commit c5e35ae。在确认这个 commit 的内容、价值和备份引用之前，hard reset 会把当前分支直接移到另一个点并覆盖工作区/index。即使对象暂时可通过 reflog 找回，也是在主动降低可恢复性。

第三问：前端 66 个 commit 应该怎么进 main？

不是把“66 个 commit 全保留”作为目标，而是把“这些历史中仍然需要的产品/工程行为”作为目标。先从最新 main 创建 integration 分支，在非生产环境做合并或重放，处理冲突后跑测试。若历史非常嘈杂，也可以通过分段 cherry-pick、重新整理 commit 或将功能重新实现到新架构，但必须保留审计线索。

第四问：临时 worktree 为什么也要清点？

因为每个 worktree 有自己的 HEAD/index/working tree。主目录 clean 不代表临时 worktree 没有独有未提交改动。收敛前应执行：

git worktree list --porcelain
git status --short
git stash list
git branch --all --verbose --no-abbrev

再分别进入需要检查的 worktree 查看状态。

第五问：怎么把事实记录成机器可验证证据？

# refs
git rev-parse HEAD
git rev-parse refs/remotes/origin/main

# 图关系
git merge-base HEAD origin/main
git rev-list --left-right --count HEAD...origin/main

# 独有历史
git log --oneline origin/main..HEAD
git log --oneline HEAD..origin/main

# 未提交状态
git status --porcelain=v1
git diff
git diff --cached

这些命令分别回答“指针在哪里”“图关系是什么”“谁有独有 commits”“工作区/index 是否有独有未提交状态”，比一句“看起来差不多”更适合 Agent/CI 自动验收。

案例的真正目标：把一个看似杂乱的 Git 状态问题，转化成对象图、refs、未提交状态、构建产物四张清单；然后只对有独有信息的地方做保护和集成。

⑦ 分级提示，最后就是实际答案

Hint 1 · 方向

先禁止自己想 pull/reset。把状态拆成：对象图、refs、index/working tree、worktree/stash、runtime artifact，然后分别问“哪里有独有信息”。

Hint 2 · 结构

用 ancestor/reachability 解释 ahead/behind；用 backup refs 提高可恢复性；复杂集成放到最新 main 派生的非生产分支；部署最后做。

Hint 3 · 接近答案

最终证明不是“SHA 看起来一样”，而是 GitHub main = origin/main = local main = M，并且运行镜像/二进制能够追溯到 M，health/smoke 通过。

答案 · 实际答案

参考答案的主线：把“同步 Git”从一个命令问题改写成一个状态收敛问题。

阶段 0：定义权威与禁止动作

先定义 GitHub main 是最终 canonical 线，但在完成独有历史清点之前，禁止任何会降低可恢复性的操作：reset --hard、clean -fd、删除分支/worktree、强推覆盖远端。canonical 并不意味着其他状态可以不经检查直接丢弃。

阶段 1：只读 inventory

git status --porcelain=v1
git rev-parse HEAD
git rev-parse main
git rev-parse origin/main
git worktree list --porcelain
git stash list
git branch --all --verbose --no-abbrev

git merge-base HEAD origin/main
git rev-list --left-right --count HEAD...origin/main
git log --oneline origin/main..HEAD

输出要结构化记录：每个 ref 的 SHA、比较对象、ahead/behind、独有 commit、dirty files、stash、worktree。此阶段目标不是修，而是把“未知”变成事实。

阶段 2：保护所有独有信息

git branch backup/server-c5e35ae c5e35ae
git branch backup/frontend-a0580dec a0580dec

# 如果需要跨机器恢复，应把明确 backup ref 推到受控远端
# git push origin backup/server-c5e35ae
# git push origin backup/frontend-a0580dec

若 worktree 有未提交内容，先明确 commit 到备份分支或用可审计方式保存；stash 只能当临时手段，不应让关键状态长期只存在 stash 中。

阶段 3：以最新 main 创建非生产集成线

git fetch origin
git switch -c integrate/frontend-20260831 origin/main

# 服务器独有热修仍有价值时，先显式重放
git cherry-pick c5e35ae

# 再集成前端历史（示意）
git merge backup/frontend-a0580dec

如果出现 48 个冲突，逐功能处理，并结合最新 main 的架构判断保留语义。不能把“全部 ours”或“全部 theirs”当默认策略。冲突解决后跑单元测试、构建、关键浏览器/CLI smoke 和必要回归。

阶段 4：只有验收通过才更新 main

假设验收后的 commit 为 M。此时才把 canonical main fast-forward/合并到 M 并推送。CI 与评审关注的是 M 的完整证据，而不是“我的集成分支本地能跑”。

阶段 5：服务器部署收敛

git fetch origin
git switch main
git merge --ff-only origin/main

git rev-parse HEAD
git rev-parse origin/main
git status --porcelain=v1

--ff-only 的价值是：如果服务器 main 有未解释分叉，它会直接拒绝偷偷制造新的 merge commit。若失败，重新回到 inventory，而不是立刻 hard reset。

阶段 6：证明真正运行的是 M

这是很多 Git 教程缺的一步。若系统通过 Docker、Go 二进制、Node build 或其他 artifact 发布，还要核对：

# 例：应用自己暴露版本
curl -sS https://service.example.com/version

# 例：Docker
docker inspect --format '{{.Image}}' app
docker image inspect IMAGE --format '{{json .RepoDigests}}'

# 再做业务 smoke / health
curl -fsS https://service.example.com/health

最佳实践是在 build 时把 commit SHA 写入版本端点、二进制 metadata 或 OCI image labels。这样能验证 runtime → artifact → source commit M 的可追溯关系。

八条安全不变量

  1. 任何破坏性命令之前，所有独有 commit 和未提交状态都必须有明确可恢复引用或归档。
  2. 所有 ahead/behind 结论必须携带“比较的是哪两个 refs”。
  3. origin/main 只代表 fetch 后的远端跟踪状态，不冒充 HEAD。
  4. clean 只证明未提交状态，不冒充 up-to-date。
  5. 生产服务器不作为复杂冲突的首选集成场所。
  6. 公共共享历史不在没有协调的情况下被 rebase/force-push 改写。
  7. canonical main 更新前必须有针对集成结果的测试证据。
  8. Git SHA 收敛后必须继续验证真正运行的 artifact 与同一 SHA 对应。
最终完成标准：① 需要保留的前端/服务器独有语义已进入 canonical main 或被明确归档；② local main、origin/main、GitHub main 对应同一已验收 commit M；③ 所有工作区状态可解释；④ 生产 artifact 可追溯到 M；⑤ health/smoke 通过。到这一步才叫“收敛完成”。

迁移能力

这套模型不只用于你这次的 106 服务器。以后遇到 Agent 并行分支、多个 worktree、CI checkout、release branch、hotfix、回滚，只需要持续问四个问题：对象图里发生了什么？哪些 refs 指向哪里？index/working tree 有没有独有状态？真正运行的 artifact 来自哪个 commit？ 只要这四层分开，Git 就不再是一组玄学命令。
