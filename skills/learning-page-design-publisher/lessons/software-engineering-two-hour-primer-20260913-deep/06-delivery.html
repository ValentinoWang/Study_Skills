深挖六：AI Coding 时代，真正的交付链不是“代码写完 → push”

写代码只完成了“实现候选”。软件交付还要回答：这一版是谁、测试证明了什么、部署的是不是同一个产物、线上真的生效了吗、出问题怎么恢复？

1. Git 证明源码历史，不证明线上版本

Commit 把一组源码变化封成可追溯历史节点；Branch 是指向 Commit 的移动引用；Merge / Rebase 解决历史整合。即使 main 已经是最新提交，也不能推出生产服务器正在运行它。

所以发布时要区分至少三个身份：Source Commit、Build Artifact、Running Deployment。三者应该能互相追溯。

2. 测试不是越多越好，而是证据层不同

测试 / 证据最适合证明不能单独证明
Unit Test函数、算法、小状态转换真实数据库/浏览器链路
Integration Test服务与数据库、组件之间协作完整用户体验
API Smoke关键接口基本存活所有边界和权限矩阵
E2E从 UI 到后端的关键业务链所有低层逻辑都正确
UAT / Acceptance业务目标和风险是否可接受替代技术 QA

Mock API 下的 E2E 只能证明前端在受控假后端下行为正确，不能证明真实鉴权、数据库迁移、第三方支付和部署环境正确。

3. Release Candidate 要冻结“验收对象”

如果验收期间代码仍然变化，就根本说不清“验收的是哪一版”。一个成熟 Candidate 应至少绑定：

source_commit
artifact_digest
migration_version
configuration_version
verification_report
known_risks

如果重新 build 得到不同 digest，就应该视为新候选，而不是继续沿用旧验收。

4. CI/CD 是把重复工程动作变成机器合同

CI（Continuous Integration）在代码变化后自动执行 build、test、lint、type check、contract test 等。Continuous Delivery 让合格候选始终处于可发布状态；Continuous Deployment 则把满足门禁后的生产部署也自动化。

高风险系统并不意味着“不能自动化”，而是可以保留明确的人工 Acceptance 门，同时其他步骤仍然自动、可重复。

5. Deployment Readback：部署命令成功，不等于用户看到新版本

发布以后应该从真实环境读回：页面版本标识、API build SHA、健康状态、关键业务接口。这样才能证明“刚才验收的候选确实在线”。

6. Observability 决定出事以后你是在实验还是在猜

Logs 记录离散事件；Metrics 观察错误率、P95/P99 延迟、队列长度等时间序列；Traces 把一次请求跨多个服务串起来。成熟系统还会把 request_id、user/tenant 的非敏感标识、release version 关联起来。

7. Rollback 也有边界

切回旧 Docker image 很容易，但数据库 migration、已经发送的邮件、已经扣掉的钱、已经调用的外部 API 不一定能自动撤销。所以发布设计应该区分“代码可回滚”和“业务副作用可补偿”。有些动作需要 Compensation，而不是简单 rollback。

AI Coding 最合理的分工：Agent 负责大量可重复工作——读需求、改代码、跑单测、API smoke、Playwright、构建、整理 diff 和证据；人重点确认需求、业务不变量、高风险权限/资金逻辑，并对一个明确 Release Candidate 作最终 Acceptance。Agent 说“完成”不是证据，测试报告也不是全部证据。
练习：Agent 告诉你“200 个测试通过、构建成功、已经 push main”。还缺哪些信息，你才敢说“这版已经线上完成验收”？

参考思路：至少要知道明确候选身份、真实后端/目标 Runtime 的关键链路结果、数据库迁移状态、部署是否使用同一 artifact、线上 readback、关键负向权限/资金测试，以及有权主体是否接受该候选。
