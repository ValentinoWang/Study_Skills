Deep Dive 03 · 约 14–18 分钟

深挖三：鉴权真正难的不是登录，而是“谁能对哪条数据做什么”

0. 本节先认词 / 先认变量

词或变量中文直觉例子
user_id当前用户的唯一编号。区分“是谁在发请求”。
tenant_id当前机构/租户的唯一编号。俱乐部 A 和俱乐部 B 是两个 tenant。
resource_id当前被操作资源的编号。某份计划、某个训练组。
role用户在组织里的角色。coach、athlete、admin。
action用户准备做的动作。read、edit、publish、delete。
relation用户和资源之间的关系。“这个教练是否真的管理这个训练组”。
Authentication · 身份认证确认“你是谁”。登录、Session、Token。
Authorization · 授权确认“你能不能对当前资源做当前动作”。能否发布这份计划。
RBACRole-Based Access Control，基于角色的权限控制。coach 可以 publish，athlete 不可以。
ABACAttribute-Based Access Control，基于属性的权限控制。还要看机构、资源归属、状态等属性。

1. Session、Cookie、Token、JWT 都只是“维持身份”的手段

Session 可以理解为服务端保存的登录会话；Cookie 是浏览器保存并自动携带的小段数据；Token 是客户端主动携带的身份凭证；JWT 是 JSON Web Token，一种带签名的 Token 格式。

它们解决的是“服务端如何知道这个请求来自谁”。但即使 Token 里写着 role=coach，也不能因此允许他编辑所有机构的所有计划。

2. 真实授权往往是多个条件的 AND

先解释下面变量：authenticated 表示身份是否有效；same_tenant 表示用户和资源是否属于同一租户；role_allows(action) 表示角色是否允许这个动作；has_relation 表示用户和资源是否有业务关系；state_allows 表示资源当前状态是否允许这个动作。

allow = authenticated
        AND same_tenant
        AND role_allows(action)
        AND has_relation(user, resource)
        AND state_allows(action)

AND 的意思是“并且”：所有条件都成立，allow 才是真。

例如教练发布训练计划，需要同时满足：账号有效；属于这个机构；角色允许 publish；确实管理这个训练组；计划当前仍处于可发布状态。

3. 为什么 RBAC 一个人通常不够

RBAC 擅长回答“这个角色大体能干什么”，但不能单独回答“能不能操作这一条具体数据”。例如两个用户都是 coach，一个管理短跑一组，一个管理跳远组。只判断角色会让二者都拥有同样的资源范围。

所以真实 SaaS 常常是：Role + Tenant + Resource Relation + Resource State 一起判断。

4. 多租户最怕“改个 ID 就看到别人数据”

假设页面从来不展示机构 B 的计划，但用户手工调用：

GET /api/plans/98765

这里 98765 只是某份计划的 resource_id。如果后端只按这个 ID 查数据库然后返回，就可能出现对象级越权。

正确思路通常是：查询和授权都带上当前 tenant_id，再校验用户和资源的 relation。前端隐藏按钮只是体验优化，不是安全边界。

5. Audit Log 和普通 Debug Log 不一样

Audit Log（审计日志）记录高价值业务动作，用于回答“谁、什么时候、对哪个对象、做了什么”。典型字段包括 user_id、tenant_id、resource_id、action、version、request_id。

request_id 是一次请求的追踪编号，方便把前端报错、后端日志和审计事件串起来。

练习：“普通用户页面里根本看不到删除按钮，所以删除 API 不需要再验权限。”错在哪？

答案：浏览器完全可以被用户控制。用户可以自己构造 HTTP 请求。真正的安全条件必须由服务端针对当前 user、tenant、resource、action 再做一次授权判断。
