深挖二：数据库不是仓库，而是“守住事实”的机器

0. 本节先认词 / 先认变量

词或变量先把它理解成什么例子
Database · 数据库长期保存结构化事实，并负责约束、并发和事务的系统。保存用户、训练计划、订单、训练记录。
Table / Row / Column表 / 行 / 列。表像一类对象，行像一条记录，列像对象的某个属性。plans 表里一行可以是一份训练计划。
Schema数据库结构定义：有哪些表、字段、类型和约束。规定 plan_id、status、version 等字段。
id / Primary Key一条记录自己的唯一身份证。plan_id=123 表示第 123 号计划。
Foreign Key一条记录引用另一条记录的关系。训练记录里的 plan_version_id 指向实际执行的计划版本。
Constraint · 约束数据库自己强制执行的规则。某字段不能为空；某业务键必须唯一。
Transaction · 事务把多步数据库变化当成一个不可分割动作。记账和扣额度要么一起成功，要么一起失败。
status对象当前业务状态。DRAFT、PUBLISHED。
version对象版本号，用来区分“我看到的是第几版”。version=7 表示当前第 7 版。
State Machine · 状态机规定有哪些状态，以及哪些状态之间允许迁移。DRAFT → PUBLISHED 可以；某些反向迁移不允许。
Race Condition · 竞态条件两个并发操作因为执行先后不同，产生了不同或错误结果。两名教练同时改同一份计划。
Migration · 数据库迁移让数据库结构从旧版本安全升级到新版本。给 plans 新增一个字段并处理旧数据。

1. CRUD 只是最表层

CRUD 是 Create（创建）、Read（读取）、Update（更新）、Delete（删除）。它告诉你数据库能做哪四类基础动作，但没有回答“哪些数据可以更新、什么时候能删、两个人一起更新怎么办”。

以训练 SaaS 为例，可以把三个对象分开：

  • plans：计划这个业务对象的“当前入口”。
  • plan_versions：每次发布/修订后形成的历史版本。
  • training_logs：运动员真实执行后产生的记录。

这里 plans、plan_versions、training_logs 只是示例表名。重点是：“计划本身”“计划的版本”“实际执行记录”不是同一个对象。

2. 不变量：真正要守的是规则，而不只是字段

Invariant（不变量）可以理解为：无论系统经历多少合法操作，都必须一直成立的条件。

  • 已经发布的历史版本不能被偷偷改写。
  • 训练记录必须知道自己执行的是哪个计划版本。
  • 同一个支付事件不能生成两条有效账本。
  • 一个机构的数据不能被另一个机构的普通账号读到。

这些规则如果只写在前端 if 里，很脆弱；越关键的不变量，越应该由数据库约束、唯一索引、事务和服务端规则一起兜底。

3. Transaction 为什么解决“一半成功”

先认代码里的两个关键词：BEGIN 表示“事务开始”，COMMIT 表示“确认提交”。

BEGIN
INSERT usage_event ...
INSERT ledger_entry ...
UPDATE quota ...
UPDATE invoice ...
COMMIT

逐行翻译：

  • usage_event：记录这次到底用了多少服务。
  • ledger_entry：账本里新增一条金额/额度变化记录。
  • quota：用户剩余额度。
  • invoice：账单。

如果这四件事在业务上是一体的，就不希望只做完前两件服务器就挂掉。Transaction 的作用就是尽量让它们表现为“整体成功”或“整体失败”。

4. ACID 四个字母先翻译成人话

字母全称人话
AAtomicity · 原子性不留半成品
CConsistency · 一致性操作前后都不能违反约束
IIsolation · 隔离性并发事务尽量不要互相踩坏
DDurability · 持久性一旦提交，结果应可靠保存

5. 状态机不是“有个 status 字段”

DRAFT
  ↓ publish
PUBLISHED
  ↓ execute
IN_EXECUTION
  ↓ complete
COMPLETED
  ↓ review
REVIEWED

这里 publish、execute、complete、review 是“触发状态变化的动作”。状态机真正规定的是：哪些动作在当前状态下合法。

所以“已发布以后为了方便继续改，直接把 status 改回 DRAFT”通常很危险。更合理的是保留已发布的 v7，再创建新的 draft v8。

6. 并发更新为什么会把别人改动覆盖掉

先定义：v7 就是版本 7，v8 是版本 8。A、B 两位教练同时看到 v7。A 先保存，服务器变成 v8。B 还拿着旧 v7 保存，如果服务器不检查版本，就可能把 A 的修改覆盖掉。这叫 Lost Update（丢失更新）。

Optimistic Locking（乐观锁）的一种写法：

UPDATE plans
SET content = ?, version = 8
WHERE id = 123 AND version = 7;

逐个解释：content 是计划内容；? 是稍后传入真实内容的参数占位符；id=123 指具体计划；version=7 表示“只有服务器仍然是我看到的旧版本 7 时，才允许这次更新”。如果服务器已经是 v8，这次 UPDATE 会匹配不到记录，应返回冲突。

7. Migration：数据库结构自己也有版本

例如现在要给 plans 增加 coach_note。不能只改代码，因为旧数据库没有这个字段。常见安全思路是：

expand → backfill → switch → contract

翻译：先新增兼容结构（expand）→ 给旧数据补值（backfill）→ 新代码切过去（switch）→ 确认旧逻辑不用后再删旧结构（contract）。

练习：为什么“计划已经发布，但为了继续编辑，我们把 status 直接改回 draft”通常是坏设计？

答案：因为这会让历史事实倒退。已经收到或执行 v7 的运动员仍需要一个稳定的 v7。正确思路通常是保留 v7，再创建 v8 draft。
