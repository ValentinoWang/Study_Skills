深挖四：异步、Webhook、幂等与支付，为什么会成为生产级难点

0. 本节先认词 / 先认变量

词或变量中文直觉例子
Synchronous · 同步当前步骤没结束，调用方就继续等。用户点保存，等数据库写完再返回。
Asynchronous · 异步核心动作完成后，后续工作可以慢慢做，不让用户一直等。发布计划成功后，通知 300 个运动员可以后台发送。
Queue · 队列等待后台处理的任务列表。“给运动员发推送”先进入队列。
Worker后台真正拿任务来执行的进程。从 Queue 取一条通知任务并发送。
Retry · 重试失败或超时后重新执行。推送接口暂时失败，过一会再试。
Webhook外部平台主动调用你的 HTTP 接口来通知事件。支付平台通知“这笔付款成功了”。
event_id某个外部事件的唯一编号。用它判断“这个 Webhook 我是不是已经处理过”。
Idempotency · 幂等同一个业务意图重复到达，最终副作用只发生一次。支付成功通知来 5 次，余额也只加一次。
idempotency_key一次业务意图的唯一身份。网络重试时复用同一个 key。
balance账户余额。balance += 100 表示余额增加 100。
quota剩余可用额度。还有多少 API 次数或服务金额。
Ledger · 账本每次余额/额度变化的可追溯记录。不是只保存最终 balance，而是保存每一笔为什么变。

1. 为什么要异步

发布计划时，真正必须同步确认的通常只有核心事实：“这份计划版本是否成功发布”。给 300 个运动员发通知、调用 AI 生成摘要、生成报表，可以放到后台。

HTTP Request
→ 核心事务
→ 写入 Queue
→ Response 返回给用户
              ↓
            Worker
              ↓
     Push / AI / Email

这里 HTTP Request 是用户发来的请求；核心事务 是必须当场确认的数据库变化；Queue 保存待处理任务；Worker 在后台执行。

2. 为什么 Retry 会逼出幂等问题

系统很难保证每个消息“恰好只送一次”。现实里更常见的是：宁愿重复，也别无声丢失。这类语义常被称为 at-least-once delivery，中文可以理解为“至少送达一次，因此可能送达多次”。

于是业务必须能安全处理重复，这就是幂等。

3. 先定义 business key，再谈去重

假设手机离线上传训练记录。先定义两个变量：

  • athlete_id：哪位运动员。
  • local_log_uuid：手机在本地生成的这条训练记录的唯一编号。
business_key = athlete_id + local_log_uuid

这句话读成：“一条训练记录的业务身份，由运动员身份 + 本地唯一记录号共同决定。” 手机重试 5 次都复用同一个 local_log_uuid，数据库对这个业务键做唯一约束，就能避免生成 5 条重复记录。

4. Webhook 为什么不能假设只来一次

先验签并核对支付交易、金额、币种，再处理业务。验签确认通知来自可信平台；下面的数据库事务把唯一业务占位、账本分录、余额变化一起提交。不能先单独写“已处理”，随后才尝试入账。

接收并验证通知
→ 在同一事务内判定是否已提交该业务效果
→ 首次：唯一占位 + 写账本 + 改余额一起提交
→ 重复且已提交：不再入账
→ 提交成功后返回结果

提交前故障不能吞掉重试；提交后响应丢失不能重复记账。真实异步系统还需区分“已持久接收”和“业务已完成”；这里仅展示一个受控的同步事务例子。

通知编号（event_id）：支付平台此次通知事件的标识，不等于支付交易编号。来源：支付平台提供；例子：evt_42。

业务键（business_key）：渠道、交易、业务效果共同标识的一次入账意图。来源：按渠道与业务规则派生；例子：pay_42_credit。

余额（balance）：示例账户当前可用金额，单位元。来源：数据库事务维护；例子：0 → 100 元。

账本（Ledger）：逐笔保存金额变化和原因的记录。来源：与余额同事务提交；例子：增加一笔 100 元分录。

5. “先 SELECT 再 if”为什么仍然会多加钱

请求 A: SELECT processed = false
请求 B: SELECT processed = false
A: balance += 100
B: balance += 100

先解释：processed=false 表示“数据库暂时认为这个事件还没处理”；balance += 100 表示“在原余额基础上再加 100”。

两个并发请求都可能在任何一个写入之前读到 false，于是两个 if 都通过。真正防重不能只靠应用层查询，而要用数据库 UNIQUE、事务、锁等原子机制。

6. Order、Payment、Ledger、Refund 是不同对象

对象它回答什么
Order · 订单用户想买什么、应付多少钱
Payment Transaction · 支付交易支付渠道实际发生了哪次资金尝试
Ledger Entry · 账本分录系统内部余额为什么变化
Refund · 退款原支付的全部或部分资金如何退回
Settlement · 结算支付机构何时把钱结给商户
Reconciliation · 对账你的记录与支付平台记录是否一致

7. Timeout 不是 Failure

Timeout 只表示“规定时间内没收到 Response”。第一次充值请求可能已经成功，只是响应没回来。所以创建支付/订单这类有副作用的动作，要让重试复用同一个 idempotency_key。

练习：用户连续点三次“购买套餐”。怎样区分“同一次购买的网络重试”和“用户真的想买三次”？

答案：一次明确业务意图生成一个 idempotency key；网络重试复用这个 key。用户明确重新发起一次新购买，则生成新的 key。服务端按 key 唯一，而不是简单按“用户+金额”去重。
