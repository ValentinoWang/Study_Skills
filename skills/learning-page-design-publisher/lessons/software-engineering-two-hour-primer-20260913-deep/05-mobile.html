深挖五：小程序和手机 App，真正多出来的是“平台与现实世界”

0. 本节先认词 / 先认变量

词或变量中文直觉例子
Runtime · 运行时程序真正执行代码、维护状态、调用平台能力的环境。浏览器、微信小程序运行环境、iOS/Android App。
App Lifecycle · 应用生命周期App 从启动、前台、后台、挂起到被系统回收的状态变化。锁屏后 App 可能进入后台甚至被杀死。
Local Storage · 本地存储数据保存在手机本机，而不是服务器。草稿、离线记录。
Sync · 同步把本地和服务器两边的数据重新对齐。恢复网络后上传离线训练记录。
Conflict · 冲突本地和服务器都改了同一个事实，不能简单自动合并。离线期间两端都编辑了同一条备注。
local_uuid手机本地生成的唯一记录 ID。用来识别“重试上传的还是同一条记录”。
plan_version运动员执行时所依据的计划版本。执行 v3，不等于当前服务器计划仍是 v3。
Push Notification · 推送通知服务器通过操作系统/厂商通道给手机发消息。训练提醒。
Permission · 系统权限操作系统是否允许 App 使用某项设备能力。相机、定位、蓝牙、麦克风。

1. 小程序登录为什么比普通 Web 多一层

先定义：code 是微信临时给客户端的一次性登录凭证；openid 可以理解为某个用户在某个小程序里的平台身份标识；user_id 是你自己业务数据库里的用户 ID。

wx.login()
→ 得到临时 code
→ code 发给你的后端
→ 后端向微信验证
→ 得到平台身份 openid
→ 映射到你自己的 user_id
→ 建立业务 Session / Token

这里最重要的边界是：openid 不是你的完整业务用户模型。 同一个微信用户可能在机构 A 是教练，在机构 B 是运动员。

2. 平台能力意味着平台规则

小程序除了你的代码，还受宿主平台约束：合法请求域名、支付 API、隐私接口、审核、WebView 业务域名等。于是“代码逻辑正确”不等于“平台允许这样运行”。

3. App Lifecycle：程序可能突然不再运行

先解释几个状态：Foreground 是 App 正在屏幕前台；Background 是离开当前屏幕但进程可能还在；Suspended 是系统暂时停止它继续执行；Cold Start 是完全没运行时重新启动。

Cold Start
→ Foreground
→ Background
→ Suspended
→ OS 回收进程
→ 用户重新打开
→ 从本地恢复
→ 再和服务器同步

所以关键输入不能只存在内存变量里。否则用户锁屏或系统回收进程后，刚填的训练记录可能直接消失。

4. Offline-first：本地事实和服务器事实怎么合并

假设运动员离线时执行计划 v3，并记录 100m=10.92s。这里 v3 是 plan_version=3。期间教练在服务器发布 v5。

恢复网络后，正确理解不是“手机有 v3，所以把服务器改回 v3”，而是：

  • 服务器当前计划仍然是 v5。
  • 本次训练记录保存 plan_version=3，说明当时执行的是 v3。
  • 这条本地训练记录有稳定 local_uuid，重复上传不会生成多条。
  • 如果同一条记录两端都编辑过，再进入 Conflict Resolution（冲突解决）。

5. Last Write Wins 为什么不是万能答案

Last Write Wins（LWW，最后写入者获胜）就是“谁最后保存，谁覆盖前面”。它对昵称、普通草稿可能够用；对计划版本、审批、支付、训练历史等关键事实通常不够，因为你可能需要保留两边来源和历史。

6. Push accepted 不等于用户已接受业务

先区分三个事实：

  1. 推送平台 accepted：平台接收了你要发消息的请求。
  2. 设备 displayed / received：设备可能已经展示或收到。
  3. 业务 accept：用户本人针对某个具体计划版本明确点击“接受”。

这三件事不能混成一个布尔值。

7. Permission 被拒绝本身就是一种正常状态

定位权限可能是“未请求、允许一次、使用时允许、始终允许、拒绝”。产品逻辑要明确：这个能力是核心必要，还是增强功能。

练习：短跑训练 App 想用 GPS 辅助记录，但用户拒绝定位。要不要阻止整个训练页？

答案：如果核心任务还能通过手动输入完成，就不应把增强能力缺失变成全局阻断。应该说明哪些自动分析会受影响，同时保留手动路径。
