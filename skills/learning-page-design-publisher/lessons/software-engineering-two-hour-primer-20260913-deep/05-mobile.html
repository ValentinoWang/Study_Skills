Deep Dive 05 · 约 14–18 分钟

深挖五：小程序和手机 App，真正多出来的是“平台与现实世界”

同一个后端可以同时服务 Web、小程序和 App，但移动端会额外遇到宿主平台、系统生命周期、离线、设备权限和旧版本共存。难度并不只是“多写一份 UI”。

1. 小程序登录为什么不是普通账号密码

小程序 wx.login()
→ 临时 code
→ 你的后端
→ 微信服务
→ 平台身份标识
→ 映射到你的 user_id
→ 建立你自己的 session / token

平台身份只是“这个微信账号是谁”，真正业务权限仍然属于你的用户模型。一个微信用户可能同时属于俱乐部 A 和 B，在 A 是教练，在 B 只是访客。

2. 平台能力意味着平台规则

合法请求域名、WebView 业务域名、微信支付、手机号能力、定位、相机、隐私声明、审核，都可能成为“代码没错但平台不允许”的失败原因。于是小程序开发必须同时理解你的业务规则和宿主平台规则。

3. App Lifecycle 打破“页面关了程序就结束”的直觉

Cold Start
→ Foreground
→ Background
→ Suspended
→ OS kills process
→ 用户重新打开
→ 恢复本地状态
→ 重新同步服务器

手机系统随时可能回收进程，所以关键输入不能只存在内存里。Local Storage 或 SQLite 等本地持久化会变得重要。

4. Offline-first 的核心不是“离线也能打开”，而是“离线产生的事实如何合并”

运动员在体育场没有网络，执行计划 v3 并记录 100m=10.92s、RPE=8。期间教练在服务器已经发布 v5。重新联网后，正确模型应该是：

  • 服务器 current plan 继续是 v5；
  • 这条训练记录保留自己执行时引用的 plan_version=v3；
  • 本地记录有稳定 local UUID，重试上传不会重复生成记录；
  • 如果同一条记录两端都编辑，需要明确 Conflict Resolution 规则。

Last Write Wins（最后写入覆盖）不是万能方案。对昵称、草稿备注也许可接受；对计划版本、账单、审批、成绩历史通常不够。

5. Push Notification 不能冒充业务回执

后端把消息交给 APNs、FCM 或厂商推送，平台返回 accepted，只证明“平台接收了推送任务”。后续还有设备是否在线、系统是否展示、用户是否看到、用户是否点击。即使用户点击了，也不能自动推出“接受训练计划”。

业务 Ack / Accept 应该是独立对象或明确动作：用户针对具体版本主动确认，后端记录 actor、object、version、time。

6. Permission 被拒绝是正常状态

相机、定位、麦克风、蓝牙、健康数据都可能处于“未询问 / 允许一次 / 使用时允许 / 永久拒绝”等状态。设计时要问：这项权限是核心不变量，还是增强能力？如果只是增强能力，就应该优雅降级。

练习：一个短跑训练 App 希望用 GPS 辅助记录，但用户拒绝定位。应该阻止整个训练页吗？

参考思路：如果核心任务仍可通过手动输入成绩完成，就不应因为增强能力缺失而硬阻断。应该提示定位能力缺失会影响哪些自动分析，同时保留手动记录路径。只有功能本身逻辑上依赖定位才能成立时，才需要阻断。
