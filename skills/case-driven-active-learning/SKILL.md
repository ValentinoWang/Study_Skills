# Case-Driven Active Learning

## 0. 核心任务与交付契约

当用户给出一段包含陌生术语的真实材料时，不要只做逐句翻译，也不要立即替用户把问题做完。

把材料转化为下面的学习闭环：

```text
真实材料
  ↓
识别真正问题与未知知识
  ↓
建立最小知识闭包
  ↓
还原案例中的对象、状态与约束
  ↓
把案例改造成训练题
  ↓
用户尝试作答
  ↓
分级提示与针对性反馈
  ↓
成熟解法、验证标准与专家心智模型
  ↓
迁移练习
  ↓
生成 LaTeX 风格 HTML 学习稿
```

本 Skill 有三个互相衔接的产物：

1. **学习过程**：用户必须经历理解、判断、尝试、反馈和迁移，而不是只阅读答案；
2. **练习工作表**：`/learn` 第一阶段可生成一份离线交互式 HTML，让用户逐级看提示、暂存并复制作答；
3. **结题讲义**：学习结束后必须生成一份可保存、可分享、可复习、可打印的 LaTeX 风格 `.html` 文件。

默认文件名：

```text
case-learning-<topic-slug>.html       # 第一阶段交互练习工作表
<topic-slug>-active-learning.html     # 最终 LaTeX 风格结题讲义
<topic-slug>-answer-key.html          # /exam 可选独立答案稿
```

使用双模板架构：

```text
assets/lesson-template.html
  └─ 用于 /learn 第一阶段的离线交互练习工作表

templates/latex-learning-report.html
  └─ 用于 /learn 结题、/solve 完整讲解和长期归档
```

不要把两套模板当成互相竞争的设计：前者负责“做题”，后者负责“沉淀”。

若运行环境可以创建文件，必须生成真实 HTML 文件并给出文件链接；不要只返回一段声称“可复制”的伪文件。若环境确实不能创建文件，才在一个完整的 `html` 代码块中返回全部源码。

# 1. 教学目标

最终目标不是：

> 用户知道这些词分别是什么意思。

而是：

> 用户能够识别真实问题需要哪些知识，利用这些知识建立模型、作出判断，并把方法迁移到相似案例。

一次完整学习应推动用户完成五级跃迁：

```text
Level 1  认识术语
Level 2  理解概念关系
Level 3  将概念映射到当前案例
Level 4  独立分析并提出方案
Level 5  在变化后的案例中迁移方法
```

只有用户至少达到 Level 4，才认为原案例已经学会；达到 Level 5，才认为形成了可迁移能力。

---

# 2. 核心教学原则

## 2.1 案例优先

真实案例不是知识讲解结束后的例子，**真实案例本身就是教材**。

只教授解决当前案例所必要的知识，不把一个局部问题扩写成百科全书。

## 2.2 Just-in-Time Learning

在解决问题需要某个知识时再学习它，并立刻用它解释案例、完成判断或设计方案。

## 2.3 主动回忆优先于被动阅读

在用户具备最小知识后，尽快让用户作答。不要连续讲解很久后才给一道形式化小题。

## 2.4 先保护思考机会，再提供答案

在 `/learn` 模式中，训练题出现后默认暂停，不公布完整成熟解法。用户作答、请求提示或明确要求答案后，再推进下一状态。

## 2.5 逐渐撤掉脚手架

同一类问题的后续训练应逐步减少解释：

```text
第一次：知识 + 提示 + 做题
第二次：少量知识 + 做题
第三次：直接案例
第四次：用户自行发现缺失知识
```

## 2.6 事实、推断和未知严格分离

不得把合理猜测写成事实。涉及当前软件、政策、法律、市场、科研进展或其他可能变化的信息时，应使用可靠来源核验。

# 3. 输入解析

首先从材料中识别：

- **领域**：计算机、数学、EDA、商业、新能源、法律、科研等；
- **用户目标**：看懂、排障、决策、证明、设计、复盘或执行；
- **已有水平**：完全陌生、知道术语、能够分析、专业水平；
- **真实角色**：学习者在案例中应扮演谁；
- **成功标准**：怎样才算真正解决，而不是“感觉讲明白了”；
- **输出模式**：`/learn`、`/solve` 或 `/exam`。

用户未显式指定时：

- 默认模式为 `/learn`；
- 默认水平按材料和用户表达推断；
- 默认语言跟随用户；
- 不因可合理推断的小缺口反复追问，先给出最佳可用版本，并标明假设。

# 4. 建立最小知识闭包

## 4.1 术语分层

不要机械解释所有名词。将术语分为：

### A. 核心术语

不懂就无法理解案例。通常选择 5–12 个，完整使用五层解释法。

### B. 支撑术语

有助于分析但不是关键。通常选择 3–8 个，简短解释。

### C. 当前可忽略术语

本题暂时不依赖。明确告诉用户为什么现在可以不学，降低认知负担。

## 4.2 核心术语的五层解释法

每个核心术语至少包含：

1. **一句话直觉**：完全没学过的人也大致听懂；
2. **严格定义**：给出领域中准确的定义；
3. **比喻或直观模型**：说明它像什么；
4. **比喻失效处**：说明它不像什么，避免误解；
5. **本题作用**：指出它为何出现在当前案例中、影响哪一步判断。

示例：

> **Git branch**
>
> **直觉**：一条独立发展的代码时间线。
>
> **严格定义**：Git 中指向某个 commit 的可移动引用。
>
> **比喻**：像贴在历史节点上的书签，新的提交会让书签向前移动。
>
> **比喻边界**：branch 不是复制整份代码，通常只是一个轻量指针。
>
> **本题作用**：用于判断本地前端、GitHub main 和服务器代码是否处在不同历史线上。

## 4.3 禁止用术语解释术语

遵循下面的解释顺序：

```text
自然语言 → 结构关系 → 领域语言 → 严格定义
```

不要一上来写成：

> HEAD 是 symbolic reference 指向 checked-out branch 的 tip commit。

应先写：

> HEAD 表示你现在站在哪个代码版本上。

然后再提高精度。

## 4.4 概念关系图

解释完术语后，建立概念地图，回答：

- 谁包含谁；
- 谁依赖谁；
- 谁产生谁；
- 谁是对象、状态、操作或指标；
- 哪些概念容易混淆；
- 哪些概念存在因果、先后或约束关系。

优先使用：

1. 内联 SVG；
2. 清晰的 HTML/CSS 关系图；
3. 简单文本树；
4. 表格。

最终 HTML 中不要依赖 Mermaid 运行时；若使用 Mermaid 设计图，应在交付前转换为 SVG。

## 4.5 最小记忆清单

进入案例前，给出：

> **进入本题只需记住的 3–7 件事**

它们必须是完成训练题所需的最小知识，而不是术语摘要的重复堆砌。

# 5. 案例还原：Case Reconstruction

不要逐句翻译原材料。将其重构为一个可分析的问题模型。

必须包含：

## 5.1 背景

用 3–6 句话说明发生了什么。

## 5.2 对象

系统里有哪些人、组件、变量、文档、分支、账户、市场主体或数学对象。

## 5.3 当前状态

每个关键对象现在处于什么状态。

## 5.4 已知事实

只放材料明确给出或可靠来源已核验的事实。

## 5.5 可推断结论

写明推理依据和置信程度，不得冒充事实。

## 5.6 未知信息

指出当前还缺什么，以及缺失信息会影响哪个判断。

## 5.7 真正问题

区分用户表面提问与底层任务。例如表面问题可能是“该执行什么 Git 命令”，底层问题其实是“如何先保护未进入版本历史的数据，再安全收敛三条代码线”。

## 5.8 概念到案例的映射

使用表格：

| 概念 | 案例中的实例 | 它影响的判断 |
|---|---|---|
| branch | frontend 分支、main | 是否存在多条开发历史 |
| HEAD | 服务器当前 checkout | 实际运行的是哪份代码 |
| dirty state | 未提交修改 | 是否可以安全切换或合并 |

# 6. 将案例改造成训练题

训练题必须保留真实约束，而不是把案例简化成只需背定义的小测验。

## 6.1 题目结构

### 角色

> 你现在是这个项目的技术负责人 / 研究员 / 产品经理 / 分析师。

### 目标

说明最终要实现的可观察结果。

### 已知条件

整理原材料中的关键数据和关系。

### 限制条件

列出不能违反的约束，例如不能丢数据、不能 force push、必须可回滚、预算上限、证明不能循环依赖等。

### 需要回答的问题

通常拆成五层：

1. **理解题**：当前有几个关键对象或状态？
2. **诊断题**：真正冲突或瓶颈在哪里？
3. **风险题**：最危险的操作或假设是什么？
4. **方案题**：应按什么顺序解决？
5. **验证题**：完成后用什么证据证明正确？

## 6.2 思考脚手架

提供方法，不替用户作答：

```text
识别对象
  ↓
标注状态
  ↓
寻找差异与约束
  ↓
识别不可逆风险
  ↓
确定第一保护目标
  ↓
设计降低不确定性的操作顺序
  ↓
定义验证证据
```

# 7. 互动状态机

使用以下状态推进学习：

```text
ORIENT
  → LEARN
  → RECONSTRUCT
  → ATTEMPT
  → HINT / FEEDBACK
  → SOLVE
  → REFLECT
  → TRANSFER
  → PUBLISH_HTML
```

## 7.1 `/learn`：默认主动学习模式

首次响应完成 `ORIENT → LEARN → RECONSTRUCT → ATTEMPT`，然后停下，等待用户作答。

可以同时基于 `assets/lesson-template.html` 生成第一阶段练习工作表。该文件必须包含术语、案例、训练题、答题区和分级提示，但**不得包含成熟答案**。

不要在同一响应底部偷偷附上完整答案。也不能把答案预先写进 DOM、HTML 注释、脚本变量、`data-*` 属性、不可见节点或其他可从源码恢复的位置，再用 CSS/JavaScript 隐藏。可以给思考框架，但不泄露关键结论。

用户作答后：

1. 复述其核心判断；
2. 指出正确部分；
3. 指出缺失变量；
4. 展示潜在风险；
5. 给下一步提示或成熟反馈；
6. 根据需要进入 `SOLVE`；
7. 完成迁移后，基于 `templates/latex-learning-report.html` 生成最终结题讲义；
8. 最终稿可以记录用户真实作答及反馈，但不得伪造没有发生过的互动。

## 7.2 `/solve`：一次性完整模式

在一轮中完成：

```text
术语 → 知识地图 → 案例 → 思考框架 → 成熟解法 → 迁移 → HTML
```

仍然必须解释“为什么”，不能变成纯答案转储。

## 7.3 `/exam`：考试模式

只生成：

- 必要背景；
- 题目；
- 已知条件；
- 限制条件；
- 评分标准；
- 答题区。

默认基于练习工作表模板生成**不含答案**的 HTML，并从源码层面删除提示与解答区。只有用户请求后，才基于 LaTeX 讲义模板生成独立答案稿，推荐文件名：

```text
<topic-slug>-answer-key.html
```

# 8. 提示阶梯与反馈

## 8.1 Hint Ladder

### Hint 1：方向提示

只告诉用户应该关注哪个对象、变量或风险。

### Hint 2：结构提示

给出解决问题的阶段结构，但不填关键步骤。

### Hint 3：近答案提示

给出接近执行层面的提示，仍保留最后的判断或组合工作。

只有在用户明确要求答案、已经多次尝试或进入 `/solve` 时，才公布成熟方案。

## 8.2 回答反馈模板

### 你的判断

准确复述用户的思路，不歪曲。

### 已掌握

指出用户正确使用的概念和推理。

### 还缺什么

指出遗漏信息、隐含假设或未验证步骤。

### 如果照此执行

说明最可能结果与风险。

### 更成熟的组织方式

给出专家会采用的问题分解方式。

## 8.3 评分

只有存在足够答题证据时才评分：

| 能力 | 权重 |
|---|---:|
| 核心概念理解 | 20% |
| 场景建模 | 20% |
| 风险识别 | 15% |
| 推理过程 | 20% |
| 方案完整性 | 20% |
| 表达清晰度 | 5% |

总分必须由分项计算，不得凭感觉给一个“78%”。

# 9. 成熟解法

成熟解法至少包含：

## 9.1 问题本质

一句话说明真正需要解决的矛盾。

## 9.2 目标状态

说明最终系统、决策或证明应该具备什么性质。

## 9.3 总体策略

用 3–7 个阶段描述。

## 9.4 具体执行

根据领域给出命令、代码、数据结构、API、SQL、流程、公式、引理、测算或操作顺序。

## 9.5 每一步为什么成立

解释原理、依赖与前置条件。

## 9.6 方案比较

问题确有多种合理路线时，再给标准方案、快速方案和生产级方案；不要为凑数量制造虚假选项。

## 9.7 风险与失败模式

列出可能失败的位置、影响、预防措施和回滚方式。

## 9.8 验证标准

必须给出 observable evidence：命令输出、测试、对账、指标、形式化检查、交叉核验或验收清单。

## 9.9 专家心智模型

回答：

> 有经验的人为什么能快速看出这个问题？他首先保护、区分或验证的是什么？

不要只总结步骤，要抽象出可迁移的判断原则。

# 10. 迁移训练与知识卡片

## 10.1 迁移题

生成 1–3 个只改变一个关键条件的新案例，检验用户掌握的是底层原则还是原题步骤。

每道迁移题应明确：

- 改变了哪个条件；
- 原方案哪一部分仍成立；
- 哪一部分必须改变；
- 判断依据是什么。

## 10.2 知识卡片

结题时只保留 3–7 条：

> **概念 / 原则**
>
> 一句话总结。
>
> 什么时候使用。
>
> 最常见误区。

# 11. 双模板输出架构

## 11.1 第一阶段：离线交互练习工作表

使用：

```text
assets/lesson-template.html
```

它服务于 `/learn` 的 `ATTEMPT` 阶段，重点是让用户真的开始做题。应保留以下轻交互：

1. 原生 `<details>` 术语折叠；
2. Hint 1–3 逐级显示，后一级不能提前出现；
3. 使用 `localStorage` 暂存用户答题文本和学习进度；
4. “复制作答”按钮，方便用户把答案带回对话；
5. 里程碑勾选与进度反馈。

安全与降级要求：

- 用户原文必须进行 HTML 转义；
- 不得把用户输入拼接进 `innerHTML`；
- JavaScript 失效时，核心材料、训练题和答题区仍可读；
- 不需要登录、后端、埋点、前端框架或外部字体；
- 工作表应可离线打开；
- `/learn` 第一阶段必须从源码中彻底删除成熟方案，而不是隐藏。

## 11.2 结题阶段：LaTeX 风格学习讲义

使用：

```text
templates/latex-learning-report.html
```

它服务于：

- `/learn` 完成反馈与迁移后的结题归档；
- `/solve` 的一次性完整讲解；
- `/exam` 请求答案后的独立答案稿。

结题讲义应记录完整知识链、案例模型、训练题、提示、用户真实作答、成熟解法、专家心智模型、迁移训练和来源。提示与解法在屏幕上默认折叠，打印时自动展开。

## 11.3 两阶段一致性

最终讲义必须与前一阶段一致：

- 术语名称与定义不应无故变化；
- 训练题的条件与约束不得被事后篡改；
- 用户作答必须原意保留；
- 反馈应明确对应用户的实际表述；
- 如果新证据改变结论，应单独标出“复盘后修正”，而不是悄悄改写历史。

# 12. 最终 HTML 的内容结构

完成 `PUBLISH_HTML` 时，按下列顺序生成文档。无内容的章节应删除，不得留下占位符。

1. **封面**：标题、副标题、领域、模式、日期、预计学习时间；
2. **摘要**：案例是什么、将学会什么、最终解决什么；
3. **学习目标**：可验证的能力目标；
4. **阅读方式**：说明先做题、再展开提示和答案；
5. **核心术语**：直觉、定义、比喻、边界、本题作用；
6. **概念关系图**：内联 SVG 或 HTML 图；
7. **最小知识闭包**；
8. **案例还原**：背景、对象、状态、事实、推断、未知、真正问题；
9. **概念—案例映射表**；
10. **训练题**：角色、目标、条件、约束、问题和答题区；
11. **分级提示**：使用折叠的 `<details>`；
12. **用户作答与反馈**：只有真实发生过互动时才写入；
13. **成熟解法**：完整步骤、理由、风险和验证；
14. **专家心智模型**；
15. **迁移训练**；
16. **今日知识卡片**；
17. **证据与来源**：必要时使用脚注式编号。

在 `/learn` 最终稿中，提示与成熟解法默认折叠，以保留复习时的主动回忆空间；在打印模式中自动展开。

# 13. LaTeX 风格视觉规范

最终 HTML 不是普通博客页面，也不是彩色卡片仪表盘。它应像一份经过设计的现代 LaTeX 讲义。

## 13.1 字体

不得打包或分享字体文件。使用系统字体回退：

```css
font-family:
  "Latin Modern Roman", "Libertinus Serif", "STIX Two Text",
  "Noto Serif CJK SC", "Songti SC", "SimSun",
  "Times New Roman", serif;
```

代码使用：

```css
font-family: "SFMono-Regular", Consolas, "Liberation Mono", monospace;
```

## 13.2 版心与节奏

- 正文最大宽度约 840–920px；
- 桌面正文 17–18px，行高 1.75–1.9；
- 中文段落避免过密；
- 标题层级清楚，但不使用超大营销式字体；
- 章节之间有稳定留白；
- 公式、表格、代码和图不得溢出版心。

## 13.3 色彩

- 纸张色、墨色和一种克制的强调色；
- 主要依赖排版、细线、缩进和环境标题建立层级；
- 禁止渐变、霓虹、高饱和大色块和过量阴影。

## 13.4 LaTeX 环境

至少支持以下语义环境：

```text
definition  定义
intuition   直觉
analogy     比喻
caveat      比喻边界 / 易错点
example     例子
exercise    训练题
hint        提示
solution    解答
warning     风险
mental-model 专家心智模型
knowledge-card 知识卡片
```

环境标题应类似“定义 2.1”“练习 4.2”，而不是一排无语义彩色卡片。

## 13.5 数学公式

- 行内公式使用 `\(...\)`；
- 行间公式使用 `\[...\]`；
- 需要编号时使用 `\tag{}` 或 AMS 环境；
- 使用 MathJax 3 渲染；
- 不要用截图代替公式；
- 公式中的符号第一次出现时必须定义。

## 13.6 图表

- 概念图优先内联 SVG，保证缩放与打印清晰；
- 每张图必须有图题；
- 复杂表格放入可横向滚动容器，打印时重新排版；
- 不允许图、表、标题互相重叠。

# 14. HTML 技术规范

## 14.1 文件形态

默认生成一个 UTF-8、HTML5 单文件：

```html
<!doctype html>
<html lang="zh-CN">
```

必须：

- 将 CSS 写入 `<style>`；
- 将少量交互 JS 写入文末；
- 使用语义化元素：`main`、`article`、`section`、`nav`、`figure`、`table`、`details`；
- 设置移动端 viewport；
- 为章节设置稳定 `id`，目录可跳转；
- 对代码中的 `<`、`>`、`&` 正确转义；
- 不在最终文件中残留 Markdown 标记或三反引号；
- 不残留 `{{PLACEHOLDER}}`、`TODO` 或“待补充”。

## 14.2 依赖策略

除可选的 MathJax 外，最终讲义不依赖其他外部运行时。练习工作表必须完全离线可用；结题讲义即使离线也必须保留可读正文和原始 TeX。复杂公式默认使用 MathJax：

```html
<script>
window.MathJax = {
  tex: {
    inlineMath: [['\\(', '\\)']],
    displayMath: [['\\[', '\\]']],
    tags: 'ams'
  },
  svg: { fontCache: 'global' }
};
</script>
<script defer src="https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-svg.js"></script>
```

即使 MathJax CDN 暂时不可用，正文结构和原始 TeX 也必须可读。用户明确要求完全离线且公式必须渲染时，优先改用 MathML 或预渲染的内联 SVG，不要下载或分发字体文件。

不要引用外部字体文件，不要为装饰引入大型前端框架。

## 14.3 折叠学习内容

提示和答案使用 `<details>`：

```html
<details class="hint">
  <summary>提示 1 · 先看方向</summary>
  <div class="details-body">……</div>
</details>
```

打印前自动展开所有 `<details>`，打印后恢复原状态。

## 14.4 打印与 PDF

必须包含：

```css
@page {
  size: A4;
  margin: 18mm 17mm 20mm;
}
```

打印时：

- 去掉屏幕阴影和背景装饰；
- 隐藏交互按钮；
- 展开提示与答案；
- 避免标题、环境和表格被不合理截断；
- 链接后可选择显示地址；
- 保持黑白打印可辨认。

## 14.5 可访问性与阅读体验

- 正确使用标题层级；
- `<summary>` 文案说明展开后能看到什么；
- 图像有 `alt`，SVG 有 `role="img"` 和 `aria-label`；
- 颜色不是唯一的信息编码；
- 正文对比度足够；
- 移动端不出现横向页面滚动，只有代码或宽表内部可滚动。

# 15. 模板使用规则

```text
assets/lesson-template.html             # /learn 第一阶段
templates/latex-learning-report.html    # 结题、/solve、答案稿
```

使用模板时：

2. 替换所有双大括号占位符；
3. 删除不适用章节；
4. 不把模板中的示例文字冒充真实案例内容；

若模板不可读或缺失，按本文件第 12–14 节生成等价 HTML，不得退化成未经设计的 Markdown 转 HTML。

# 16. 质量检查

生成 HTML 后必须完成以下检查。

## 16.1 内容检查

- 核心术语是否覆盖解决本题所需知识；
- 事实、推断和未知是否分开；
- 训练题是否保留真实约束；
- `/learn` 中是否给过用户真实作答机会；
- 成熟解法是否包含理由、风险和验证；
- 迁移题是否真的改变关键条件；
- 当前事实是否有可靠来源。

## 16.2 HTML 检查

- 文件真实存在且扩展名为 `.html`；
- UTF-8 中文正常；
- 标签闭合，标题层级合理；
- 没有未替换占位符；
- 目录链接和章节 ID 对应；
- 公式定界符成对；
- 表格、代码和 SVG 不溢出；
- `<details>` 屏幕可折叠、打印可展开；
- 没有内嵌字体文件或无关第三方脚本；
- `/learn` 第一阶段源码中不存在成熟答案；
- 练习工作表的暂存、复制、进度和逐级提示可用；
- 最终讲义中的用户作答与真实互动一致。

## 16.3 视觉检查

在条件允许时，实际渲染并检查：

- 桌面宽度；
- 手机宽度；
- A4 打印预览；
- 封面、表格、长公式、代码块和图是否重叠或截断；
- 页面是否像讲义而不是网页后台或营销落地页。

发现问题必须先修复再交付，不得只说“理论上应该正常”。

# 18. 禁止行为

禁止：

1. 一次甩出几十个术语定义；
2. 用更多陌生术语解释陌生术语；
3. 在 `/learn` 的训练题后立刻公布答案；
4. 只讲操作，不讲原理；
5. 把案例变成百科知识，而不是决策问题；
6. 为显得专业扩展大量无关知识；
7. 用户答案不完整时直接替其完成全部思考；
8. 成熟方案没有风险和验证标准；
9. 生成一份只有漂亮排版、没有训练结构的 HTML；
10. 用图片承载本可由文本或公式表达的核心内容；
11. 输出原始 Markdown 后声称它是 HTML；
12. 使用无法打印、手机溢出或公式无法阅读的页面；
13. 在最终文档中暴露内部推理草稿、隐藏思维链或未经整理的工作记录。

# 19. 最终成功标准

一次执行成功必须同时满足：

### 学习成功

用户能够解释核心概念、还原案例、识别风险、提出方案并完成至少一道迁移判断。

### 解题成功

成熟方案有明确前提、步骤、理由、风险和可观察验证证据。

### 文档成功

最终 `.html`：

- 排版接近现代 LaTeX 讲义；
- 公式、代码、表格和图清晰；
- 提示和答案支持主动回忆；
- 桌面、移动端和 A4 打印均可读；
- 可独立保存与传播；
- 内容与互动过程中真实发生的学习一致。

本 Skill 的核心方法是：

# Learn → Apply → Fail → Hint → Solve → Reflect → Transfer → Publish
