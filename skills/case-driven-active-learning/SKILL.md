# Case-Driven Active Learning

## 0. 核心任务与强制交付契约

当用户给出一段包含大量陌生术语的真实材料时，不要只做逐句翻译，也不要立即替用户把问题做完。

把材料转化为下面的主动学习闭环：

```text
真实材料
  ↓
识别真正问题与未知知识
  ↓
建立最小知识闭包
  ↓
还原案例中的对象、状态与约束
  ↓
把案例改造成训练题
  ↓
用户尝试作答
  ↓
分级提示与针对性反馈
  ↓
成熟解法、验证标准与专家心智模型
  ↓
迁移练习
  ↓
生成 HTML
  ↓
提交到 GitHub main
  ↓
返回 commit SHA 与仓库文件链接
```

### 0.1 什么才算“完成”

对于本 Skill 生成的 HTML，以下状态**不算完成**：

- 只在聊天中给出 HTML 代码；
- 只生成到 `/mnt/data`、sandbox 或其他当前会话环境；
- 只给出“下载 HTML”的本地链接；
- 只建议用户以后自己提交 GitHub；
- 只说明“目前还没有提交到 GitHub”；
- 已经写入 GitHub，但没有确认目标分支和 commit。

默认情况下，只有同时满足以下条件才算完成：

1. HTML 文件已经真实生成；
2. HTML 已写入 `ValentinoWang/Study_Skills`；
3. 写入目标是 **`main` 分支**；
4. 已获得这次写入产生的 **commit SHA**；
5. 最好重新读取目标路径，确认 `main` 上文件确实存在；
6. 最终回复明确给出仓库路径、commit SHA 和可点击的 GitHub 文件链接。

如果 GitHub 写入失败或当前环境没有写权限，必须把状态写成：

```text
LOCAL_ONLY / GITHUB_SYNC_BLOCKED
```

并明确说明“本地 HTML 已生成，但任务尚未完成 GitHub 同步”。不得把本地生成描述成最终完成。

### 0.2 默认 GitHub 发布目标

除非用户明确指定其他仓库或明确要求不要提交 GitHub，本 Skill 的默认发布目标固定为：

```text
repository: ValentinoWang/Study_Skills
branch: main
```

生成的案例 HTML 默认保存到：

```text
skills/case-driven-active-learning/examples/
```

推荐文件名：

```text
case-learning-<topic-slug>.html          # /learn 第一阶段练习稿
<topic-slug>-active-learning.html        # /learn 最终稿或 /solve 完整稿
<topic-slug>-answer-key.html             # /exam 可选答案稿
```

不要每次重新询问应该放在仓库根目录还是 Skill 目录。默认使用上面的 `examples/` 路径即可。

### 0.3 GitHub 写入规则

当可以访问 GitHub 写工具时，必须直接执行，不要停在“建议提交”。

操作顺序：

```text
生成 HTML
  ↓
确定目标文件名
  ↓
检查 main 上目标文件是否已存在
  ↓
不存在 → create file
已存在   → fetch 当前 SHA → update file
  ↓
直接写入 main
  ↓
取得 commit SHA
  ↓
重新读取目标路径进行验证
  ↓
最终回复 commit + GitHub 文件链接
```

默认直接写 `main`，**不要自行创建分支、PR 或等待用户确认**，除非用户明确要求走 PR 流程。

提交信息应短且可读，例如：

```text
feat: add git multi-state active learning example

feat: publish EDA netlist active learning lesson

update: refresh active learning case report
```

如果同一路径已经存在，不要因为重名就放弃同步；应读取当前 blob SHA 后更新，或在确有必要时生成清晰的新文件名。

### 0.4 本地文件与 GitHub 文件的关系

本地 HTML 是生成过程中的工作产物；GitHub `main` 中的 HTML 是默认正式交付物。

最终回复可以同时提供：

- sandbox / 本地下载链接；
- GitHub 仓库文件链接；
- GitHub commit SHA。

但**不能只有 sandbox 链接**。

# 1. 教学目标

最终目标不是：

> 用户知道这些词分别是什么意思。

而是：

> 用户能够识别真实问题需要哪些知识，利用这些知识建立模型、作出判断，并把方法迁移到相似案例。

一次完整学习应推动用户完成五级跃迁：

```text
Level 1  认识术语
Level 2  理解概念关系
Level 3  将概念映射到当前案例
Level 4  独立分析并提出方案
Level 5  在变化后的案例中迁移方法
```

只有用户至少达到 Level 4，才认为原案例已经学会；达到 Level 5，才认为形成了可迁移能力。

# 2. 核心教学原则

## 2.1 案例优先

真实案例不是知识讲解结束后的例子，**真实案例本身就是教材**。

只教授解决当前案例所必要的知识，不把一个局部问题扩写成百科全书。

## 2.2 Just-in-Time Learning

在解决问题需要某个知识时再学习它，并立刻用它解释案例、完成判断或设计方案。

## 2.3 主动回忆优先于被动阅读

在用户具备最小知识后，尽快让用户作答。不要连续讲解很久后才给一道形式化小题。

## 2.4 先保护思考机会，再提供答案

在 `/learn` 模式中，训练题出现后默认暂停，不公布完整成熟解法。用户作答、请求提示或明确要求答案后，再推进下一状态。

## 2.5 逐渐撤掉脚手架

同一类问题的后续训练应逐步减少解释：

```text
第一次：知识 + 提示 + 做题
第二次：少量知识 + 做题
第三次：直接案例
第四次：用户自行发现缺失知识
```

## 2.6 事实、推断和未知严格分离

不得把合理猜测写成事实。涉及当前软件、政策、法律、市场、科研进展或其他可能变化的信息时，应使用可靠来源核验。

# 3. 输入解析

首先从材料中识别：

- **领域**：计算机、数学、EDA、商业、新能源、法律、科研等；
- **用户目标**：看懂、排障、决策、证明、设计、复盘或执行；
- **已有水平**：完全陌生、知道术语、能够分析、专业水平；
- **真实角色**：学习者在案例中应扮演谁；
- **成功标准**：怎样才算真正解决，而不是“感觉讲明白了”；
- **输出模式**：`/learn`、`/solve` 或 `/exam`。

用户未显式指定时：

- 默认模式为 `/learn`；
- 默认水平按材料和用户表达推断；
- 默认语言跟随用户；
- 不因可合理推断的小缺口反复追问，先给出最佳可用版本，并标明假设。

# 4. 建立最小知识闭包

## 4.1 术语分层

不要机械解释所有名词。将术语分为：

### A. 核心术语

不懂就无法理解案例。通常选择 5–12 个，完整使用五层解释法。

### B. 支撑术语

有助于分析但不是关键。通常选择 3–8 个，简短解释。

### C. 当前可忽略术语

本题暂时不依赖。明确告诉用户为什么现在可以不学，降低认知负担。

## 4.2 核心术语的五层解释法

每个核心术语至少包含：

1. **一句话直觉**：完全没学过的人也大致听懂；
2. **严格定义**：给出领域中准确的定义；
3. **比喻或直观模型**：说明它像什么；
4. **比喻失效处**：说明它不像什么，避免误解；
5. **本题作用**：指出它为何出现在当前案例中、影响哪一步判断。

示例：

> **Git branch**
>
> **直觉**：一条独立发展的代码时间线。
>
> **严格定义**：Git 中指向某个 commit 的可移动引用。
>
> **比喻**：像贴在历史节点上的书签，新的提交会让书签向前移动。
>
> **比喻边界**：branch 不是复制整份代码，通常只是一个轻量指针。
>
> **本题作用**：用于判断本地前端、GitHub main 和服务器代码是否处在不同历史线上。

## 4.3 禁止用术语解释术语

遵循：

```text
自然语言 → 结构关系 → 领域语言 → 严格定义
```

不要一上来写成：

> HEAD 是 symbolic reference 指向 checked-out branch 的 tip commit。

应先写：

> HEAD 表示你现在站在哪个代码版本上。

然后再提高精度。

## 4.4 概念关系图

解释完术语后，建立概念地图，回答：

- 谁包含谁；
- 谁依赖谁；
- 谁产生谁；
- 谁是对象、状态、操作或指标；
- 哪些概念容易混淆；
- 哪些概念存在因果、先后或约束关系。

优先使用：

1. 内联 SVG；
2. 清晰的 HTML/CSS 关系图；
3. 简单文本树；
4. 表格。

最终 HTML 中不要依赖 Mermaid 运行时；若使用 Mermaid 设计图，应在交付前转换为 SVG。

## 4.5 最小记忆清单

进入案例前，给出：

> **进入本题只需记住的 3–7 件事**

它们必须是完成训练题所需的最小知识，而不是术语摘要的重复堆砌。

# 5. 案例还原：Case Reconstruction

不要逐句翻译原材料。将其重构为一个可分析的问题模型。

必须包含：

## 5.1 背景

用 3–6 句话说明发生了什么。

## 5.2 对象

系统里有哪些人、组件、变量、文档、分支、账户、市场主体或数学对象。

## 5.3 当前状态

每个关键对象现在处于什么状态。

## 5.4 已知事实

只放材料明确给出或可靠来源已核验的事实。

## 5.5 可推断结论

写明推理依据和置信程度，不得冒充事实。

## 5.6 未知信息

指出当前还缺什么，以及缺失信息会影响哪个判断。

## 5.7 真正问题

区分用户表面提问与底层任务。

例如表面问题可能是“该执行什么 Git 命令”，底层问题其实是“如何先保护未进入版本历史的数据，再安全收敛三条代码线”。

## 5.8 概念到案例的映射

使用表格：

| 概念 | 案例中的实例 | 它影响的判断 |
|---|---|---|
| branch | frontend 分支、main | 是否存在多条开发历史 |
| HEAD | 服务器当前 checkout | 实际运行的是哪份代码 |
| dirty state | 未提交修改 | 是否可以安全切换或合并 |

# 6. 将案例改造成训练题

训练题必须保留真实约束，而不是把案例简化成只需背定义的小测验。

## 6.1 题目结构

训练题包含：

### 角色

> 你现在是这个项目的技术负责人 / 研究员 / 产品经理 / 分析师。

### 目标

说明最终要实现的可观察结果。

### 已知条件

整理原材料中的关键数据和关系。

### 限制条件

列出不能违反的约束，例如不能丢数据、不能 force push、必须可回滚、预算上限、证明不能循环依赖等。

### 需要回答的问题

通常拆成五层：

1. **理解题**：当前有几个关键对象或状态？
2. **诊断题**：真正冲突或瓶颈在哪里？
3. **风险题**：最危险的操作或假设是什么？
4. **方案题**：应按什么顺序解决？
5. **验证题**：完成后用什么证据证明正确？

## 6.2 思考脚手架

提供方法，不替用户作答：

```text
识别对象
  ↓
标注状态
  ↓
寻找差异与约束
  ↓
识别不可逆风险
  ↓
确定第一保护目标
  ↓
设计降低不确定性的操作顺序
  ↓
定义验证证据
```

# 7. 互动状态机

使用以下状态推进学习：

```text
ORIENT
  → LEARN
  → RECONSTRUCT
  → ATTEMPT
  → HINT / FEEDBACK
  → SOLVE
  → REFLECT
  → TRANSFER
  → BUILD_HTML
  → PUBLISH_GITHUB_MAIN
  → VERIFY_GITHUB
  → DONE
```

**`BUILD_HTML` 不是结束状态。**

只要用户没有明确要求“不要同步 GitHub”，就必须继续执行到 `VERIFY_GITHUB`。

## 7.1 `/learn`：默认主动学习模式

首次响应完成 `ORIENT → LEARN → RECONSTRUCT → ATTEMPT`，然后停下等待用户作答。

可以同时基于：

```text
assets/lesson-template.html
```

生成第一阶段练习工作表。

第一阶段 HTML 必须包含术语、案例、训练题、答题区和分级提示，但**不得包含成熟答案**。

不要把答案预先写进 DOM、HTML 注释、脚本变量、`data-*` 属性、不可见节点或其他可从源码恢复的位置，再用 CSS/JavaScript 隐藏。

如果生成了第一阶段 HTML，默认也要将它同步到 GitHub `main`。

用户作答后：

1. 复述其核心判断；
2. 指出正确部分；
3. 指出缺失变量；
4. 展示潜在风险；
5. 给下一步提示或成熟反馈；
6. 根据需要进入 `SOLVE`；
7. 完成迁移后生成最终结题讲义；
8. 最终讲义同步到 GitHub `main`；
9. 返回最终稿 commit SHA。

## 7.2 `/solve`：一次性完整模式

在一轮中完成：

```text
术语 → 知识地图 → 案例 → 思考框架 → 成熟解法 → 迁移 → HTML → GitHub main
```

仍然必须解释“为什么”，不能变成纯答案转储。

## 7.3 `/exam`：考试模式

只生成：

- 必要背景；
- 题目；
- 已知条件；
- 限制条件；
- 评分标准；
- 答题区。

默认生成不含答案的 HTML 并同步到 GitHub `main`。只有用户请求后，再生成独立答案稿：

```text
<topic-slug>-answer-key.html
```

答案稿生成后同样默认提交 `main`。

# 8. 提示阶梯与反馈

## 8.1 Hint Ladder

### Hint 1：方向提示

只告诉用户应该关注哪个对象、变量或风险。

### Hint 2：结构提示

给出解决问题的阶段结构，但不填关键步骤。

### Hint 3：近答案提示

给出接近执行层面的提示，仍保留最后的判断或组合工作。

只有在用户明确要求答案、已经多次尝试或进入 `/solve` 时，才公布成熟方案。

## 8.2 回答反馈模板

### 你的判断

准确复述用户的思路，不歪曲。

### 已掌握

指出用户正确使用的概念和推理。

### 还缺什么

指出遗漏信息、隐含假设或未验证步骤。

### 如果照此执行

说明最可能结果与风险。

### 更成熟的组织方式

给出专家会采用的问题分解方式。

## 8.3 评分

只有存在足够答题证据时才评分：

| 能力 | 权重 |
|---|---:|
| 核心概念理解 | 20% |
| 场景建模 | 20% |
| 风险识别 | 15% |
| 推理过程 | 20% |
| 方案完整性 | 20% |
| 表达清晰度 | 5% |

总分必须由分项计算，不得凭感觉给一个“78%”。

# 9. 成熟解法

成熟解法至少包含：

1. **问题本质**：一句话说明真正需要解决的矛盾；
2. **目标状态**：说明最终系统、决策或证明应该具备什么性质；
3. **总体策略**：用 3–7 个阶段描述；
4. **具体执行**：命令、代码、数据结构、API、SQL、流程、公式、引理、测算或操作顺序；
5. **每一步为什么成立**：解释原理、依赖与前置条件；
6. **方案比较**：只有确有多种路线时才比较；
7. **风险与失败模式**：失败位置、影响、预防与回滚；
8. **验证标准**：命令输出、测试、对账、指标、形式化检查或验收清单；
9. **专家心智模型**：有经验的人为什么能快速看出关键点。

# 10. 迁移训练与知识卡片

## 10.1 迁移题

生成 1–3 个只改变一个关键条件的新案例，检验用户掌握的是底层原则还是原题步骤。

每道迁移题应明确：

- 改变了哪个条件；
- 原方案哪一部分仍成立；
- 哪一部分必须改变；
- 判断依据是什么。

## 10.2 知识卡片

结题时只保留 3–7 条：

> **概念 / 原则**
>
> 一句话总结。
>
> 什么时候使用。
>
> 最常见误区。

# 11. 双模板输出架构

## 11.1 第一阶段：离线交互练习工作表

使用：

```text
assets/lesson-template.html
```

它服务于 `/learn` 的 `ATTEMPT` 阶段，重点是让用户真的开始做题。应保留以下轻交互：

1. 原生 `<details>` 术语折叠；
2. Hint 1–3 逐级显示；
3. 使用 `localStorage` 暂存用户答题文本和学习进度；
4. “复制作答”按钮；
5. 里程碑勾选与进度反馈。

要求：

- 用户原文必须进行 HTML 转义；
- 不得把用户输入拼接进 `innerHTML`；
- JavaScript 失效时核心内容仍可读；
- 不需要登录、后端、埋点、前端框架或外部字体；
- 工作表应可离线打开；
- `/learn` 第一阶段必须从源码中彻底删除成熟方案，而不是隐藏。

## 11.2 结题阶段：LaTeX 风格学习讲义

使用：

```text
templates/latex-learning-report.html
```

它服务于：

- `/learn` 完成反馈与迁移后的结题归档；
- `/solve` 的一次性完整讲解；
- `/exam` 请求答案后的独立答案稿。

结题讲义应记录完整知识链、案例模型、训练题、提示、用户真实作答、成熟解法、专家心智模型、迁移训练和来源。

## 11.3 两阶段一致性

最终讲义必须与前一阶段一致：

- 术语名称与定义不应无故变化；
- 训练题条件与约束不得被事后篡改；
- 用户作答必须原意保留；
- 反馈应对应用户实际表述；
- 如果新证据改变结论，应单独标出“复盘后修正”。

# 13. 视觉与交互规范

最终 HTML 应像一份现代学习讲义，而不是网页后台或营销落地页。

## 13.1 视觉原则

- 页面干净、留白稳定；
- 一种主要强调色即可；
- 提示、风险、答案使用克制的语义色；
- 不使用复杂动画；
- 不引入 React/Vue 等框架；
- 不用大面积渐变、霓虹或高饱和大色块；
- 手机端自动改单栏；
- A4 打印可读。

## 13.2 术语与提示交互

默认只保留轻交互：

- 术语 `<details>` 折叠；
- Hint 逐级显示；
- textarea 作答；
- localStorage 暂存；
- 复制作答；
- 学习进度。

交互必须服务学习，不为炫技增加复杂组件。

## 13.3 公式和图

- 数学公式可使用 MathJax 3；
- 行内公式使用 `\(...\)`；
- 行间公式使用 `\[...\]`；
- 不用截图代替公式；
- 概念图优先内联 SVG；
- 图、表、代码不得溢出或重叠。

# 14. HTML 技术规范

默认生成 UTF-8 HTML5 单文件：

```html
<!doctype html>
<html lang="zh-CN">
```

必须：

- CSS 内联于 `<style>`；
- 少量 JS 放文末；
- 使用语义化元素；
- 设置 viewport；
- 章节具有稳定 id；
- 代码中的 `<`、`>`、`&` 正确转义；
- 不残留 Markdown 三反引号；
- 不残留 `{{PLACEHOLDER}}`、`TODO` 或“待补充”；
- 不打包或分享字体文件。

打印至少支持：

```css
@page {
  size: A4;
  margin: 18mm 17mm 20mm;
}
```

打印时隐藏交互按钮并展开提示和答案。

# 15. GitHub 发布检查

## 15.1 发布前

确认：

- 目标仓库是 `ValentinoWang/Study_Skills`；
- 目标分支是 `main`；
- 目标目录是 `skills/case-driven-active-learning/examples/`；

- HTML 中没有占位符或明显生成错误。

## 15.2 发布动作

直接创建到 `main`。

### 已存在文件

### 禁止

- 默认创建 PR；
- 只在本地 git commit 不 push；
- 写到其他分支后声称已经同步；

## 15.3 发布后验证

至少确认以下三个值：

```text
repository path
branch = main
commit SHA
```

条件允许时重新读取 `main` 上目标文件，确认存在。

若仓库已经配置 GitHub Pages，并且能够可靠确定页面 URL，可以额外给出在线学习地址；不能可靠确定时不要猜 URL。

# 16. 质量检查

## 16.1 内容检查

- 核心术语覆盖解决本题所需知识；

- 暂存、复制、进度和逐级提示可用。

## 16.3 GitHub 检查

- 文件不只存在 sandbox；
- `main` 上目标路径存在；
- 本次写入拿到了 commit SHA；
- 最终回复包含 GitHub 文件链接；

# 18. 禁止行为

禁止：

1. 一次甩出几十个术语定义；
2. 用更多陌生术语解释陌生术语；
3. 在 `/learn` 的训练题后立刻公布答案；
4. 只讲操作，不讲原理；
5. 把案例变成百科知识，而不是决策问题；
6. 为显得专业扩展大量无关知识；
7. 用户答案不完整时直接替其完成全部思考；
8. 成熟方案没有风险和验证标准；
9. 生成一份只有漂亮排版、没有训练结构的 HTML；
10. 输出原始 Markdown 后声称它是 HTML；
11. 使用无法打印、手机溢出或公式无法阅读的页面；
12. 在最终文档中暴露内部推理草稿或隐藏思维链；
13. HTML 生成后只给 sandbox 链接而不继续同步 GitHub；
14. 在默认情况下让用户自己决定是否要提交 GitHub；
15. 写到非 `main` 分支后声称完成；
16. 没有 commit SHA 就声称 GitHub 同步完成。

# 19. 最终成功标准

一次完整执行成功必须同时满足四类成功。

### 学习成功

用户能够解释核心概念、还原案例、识别风险、提出方案并完成至少一道迁移判断。

### 解题成功

成熟方案有明确前提、步骤、理由、风险和可观察验证证据。

### 文档成功

最终 `.html`：

- 排版美观；
- 交互克制且有助学习；
- 公式、代码、表格和图清晰；
- 桌面、移动端和 A4 打印均可读；
- 可独立保存与传播；
- 内容与真实学习过程一致。

### 发布成功

默认情况下必须满足：

```text
HTML exists locally
AND
HTML exists on ValentinoWang/Study_Skills@main
AND
commit SHA is known
AND
GitHub file link is returned
```

只完成前三类而没有“发布成功”，任务状态仍然不是 `DONE`。

本 Skill 的核心方法是：

# Learn → Apply → Fail → Hint → Solve → Reflect → Transfer → Build → Commit → Verify
