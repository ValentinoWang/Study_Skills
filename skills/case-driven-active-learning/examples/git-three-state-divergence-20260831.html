Git 三个状态为什么会不一致？

把“本地前端分支、GitHub main、106 服务器 checkout”这组真实状态，当成一次发布事故前的诊断题：先学会看清指针、历史和工作区，再决定谁该保护、谁该同步。

Orient

① 这段材料到底在说什么

一句话：你现在不是“有三份代码文件”，而是有三条不同的 Git 历史指针分别停在不同提交上；其中 GitHub 的 main 是远端权威线，106 服务器虽然已经知道这个远端最新位置，但它自己当前 checkout 的分支仍停在旧的、还带一个独有提交的历史上；与此同时，本地前端分支又从更早的共同基线独立发展了 66 个提交。

最重要的区分：
“106 服务器的 origin/main = 84382576”只说明服务器执行过足够新的 fetch，知道 GitHub main 在哪里；它不等于服务器当前 HEAD 已经到 84382576。
另一个常见误区：“工作树干净”只说明相对当前 HEAD 没有未提交修改，不说明这个 HEAD 是最新版本。

Learn

② 你必须先认识的概念

只学习解决当前案例所需的最小知识。点击术语展开五层解释。

Commit / SHA
一句话直觉
Commit 是一次“已经封存的代码版本”，SHA 是它的身份证号码。
严格定义
Git commit 是一个不可变对象，记录一棵文件树、父提交、作者/提交者信息和消息；其对象内容通过哈希得到标识符。这里的 84382576、c5e35ae 都是短 SHA。
比喻
像游戏存档：每个存档有唯一编号，你可以让不同角色停在不同存档上。
比喻失效处
Git 历史不是简单单线时间轴；merge 后可以形成有多个父节点的有向无环图。
当前案例影响
先看 SHA，才能确认 GitHub、服务器、本地分支究竟是不是同一个版本。
Branch 与 HEAD
一句话直觉
Branch 是会移动的“书签”；HEAD 表示“我当前站在哪个书签/提交上”。
严格定义
本地 branch 通常是 refs/heads/<name> 下指向某个 commit 的引用；HEAD 通常符号引用当前分支，也可能直接指向 commit（detached HEAD）。
比喻
Commit 是站点，branch 是贴在某个站点上的标签，HEAD 是“你现在站在哪条线路”。
比喻失效处
分支本身不复制一套文件；它只是一个轻量指针。
当前案例影响
106 当前 branch 是 wip/server-local-20260831，所以它实际工作的历史由 c5e35ae 决定，而不是由 origin/main 决定。
远程仓库 vs origin/main
一句话直觉
GitHub 的 main 是“远处真实的指针”；origin/main 是你本地对它最近一次看到的位置做的缓存。
严格定义
origin/main 属于 remote-tracking ref，通常位于 refs/remotes/origin/main，主要由 fetch 更新；它不是 GitHub 服务端分支对象本身。
比喻
GitHub main 像交易所实时价格，origin/main 像你手机最后刷新到的报价。
比喻失效处
这个缓存不是自动实时更新；没 fetch 时可能过期。
当前案例影响
106 的 origin/main 与 GitHub main 都是 84382576，说明“认知已同步”；但 checkout 仍未同步。
Checkout / Working Tree
一句话直觉
Checkout 决定你当前目录里展开的是哪条历史；working tree 就是你肉眼看到、程序可能使用的那些文件。
严格定义
Git 将某个 commit/branch 的树内容写入工作目录并更新 index/HEAD；工作树 clean 表示 index 与 working tree 相对 HEAD 没有待提交变化。
比喻
仓库像书库，checkout 是把某一版书真正摊在桌上。
比喻失效处
“桌上的书”未必就是线上服务真正加载的代码，真实部署还可能来自容器、构建产物或另一路径。
当前案例影响
因此“服务器 checkout 在 c5e35ae”只能证明这个工作目录的 Git 状态；若要证明线上服务版本，还要看进程/部署来源。
git worktree
一句话直觉
同一个 Git 仓库，可以同时摊开多个独立工作目录，各自在不同分支/提交上工作。
严格定义
git worktree 让多个工作目录共享对象数据库，但各自拥有 HEAD、index 与工作树状态。
比喻
同一套图书馆藏书，在两张桌子上分别摊开不同版本。
比喻失效处
它们不是完全独立克隆；底层对象是共享的，一些分支不能同时被多个 worktree 正常 checkout。
当前案例影响
codex/frontend-visual-review-mainline-20260831 是并行工作桌，不是远端权威；它落后 main 7 个提交本身不等于生产落后 7 个提交。
Merge base 与 ahead / behind
一句话直觉
先找到两条历史最后一次共同的祖先，再数双方各自从那里新增了多少提交。
严格定义
merge base 是两个提交在祖先关系中的最佳共同祖先；ahead/behind 是相对两条历史的可达 commit 集合差异，因此是成对比较，不是一个分支的全局属性。
比喻
两条道路从同一岔路口分开：A 往前走 621 站，B 往前走 66 站。
比喻失效处
提交数不等于代码量、重要性或合并难度；一个提交也可能改很多文件。
当前案例影响
“服务器 vs GitHub 的 631/1”与“前端分支 vs GitHub 的 621/66”并不矛盾，因为比较的两对对象不同。
Merge conflict
一句话直觉
Git 无法安全判断两边的修改该如何自动拼在一起，于是把决定权交给人。
严格定义
三方合并时，基于 merge base 比较 ours/theirs；当修改重叠或发生删除/重命名等无法自动裁决的结构变化时产生冲突。
比喻
两个人都改了同一句合同，机器不知道最终该保留哪一版。
比喻失效处
“冲突文件 48 个”不等于“48 个严重 bug”；有些可能是机械冲突，有些才是语义冲突。
当前案例影响
48 个冲突说明前端分支已经长期漂移，直接把它硬塞进最新 main 的集成成本不低，需要专门的整合阶段与测试证据。

记住 1

Commit 是版本；branch 是指向版本的可移动指针。

记住 2

origin/main 是本地对远端 main 的跟踪指针，不是当前 checkout。

记住 3

clean 只回答“有没有未提交修改”，不回答“是不是最新”。

记住 4

ahead/behind 必须问“相对谁”；不同成对比较可以得到不同数字。

记住 5

处理分叉时，第一目标通常不是“赶紧同步”，而是先保护所有独有历史，再收敛。

Reconstruct

④ 把真实案例重新还原

背景
同一项目同时存在本地前端开发、GitHub 主线、106 服务器工作目录和一个临时 worktree。目标显然是最终让可保留的工作进入主线，并让服务器运行一个经过验证的权威版本。
关键对象
① 本地前端分支 codex/frontend-visual-review-stages-0-3-20260830；② GitHub main；③ 106 当前分支 wip/server-local-20260831；④ 106 的 origin/main；⑤ 本地临时 worktree。

已知事实

GitHub main
84382576，当前远端权威 SHA。

106 跟踪指针
origin/main = 84382576，与 GitHub main 一致。

106 实际 checkout
wip/server-local-20260831 at c5e35ae，工作树 clean。

服务器相对 GitHub
GitHub 有 631 个独有提交，服务器有 1 个独有提交。

本地前端分支
a0580dec，尚未 push / merge / 上 106。

前端 vs GitHub
merge base 36b470e7；GitHub +621，前端 +66。

试合并
在最新 GitHub main 上合并前端分支，会冲突 48 个文件。

临时 worktree
0fb8cad7，比 GitHub main 落后 7 个提交，不是远端权威状态。

可以推断

106 已经 fetch 到最新 main，所以“远端信息不同步”不是当前主矛盾；主矛盾是实际 checkout 还在另一条分支。

本地前端分支与 main 分叉时间较早，双方都前进很多，48 个冲突很符合“长期分叉后再集成”的特征。

服务器那个 1 个独有提交必须先判断价值；它可能是要保留的 hotfix，也可能是应丢弃的本地临时提交。

尚不知道

106 上真正对外服务的进程，是否直接使用这个 checkout，还是使用 Docker 镜像/构建产物/其他目录。

c5e35ae 那 1 个独有提交具体改了什么，是否已被 main 以别的形式吸收。

48 个冲突里，哪些只是格式/重命名冲突，哪些涉及业务语义，需要逐项判断。

关键风险

为了“追 main”直接 reset 服务器分支，可能把服务器唯一提交变成难以找回的悬空历史。

为了“保前端”直接把 66 个提交强推主线，可能覆盖 621 个主线演进或制造大规模回归。

把 origin/main 已更新误判为“生产已更新”，会产生部署版本认知错误。

真正问题不是：“怎么把三个 SHA 变成一样？”
真正问题是：“如何在不丢失任何有价值独有历史的前提下，把改动集成到一个经过测试的权威主线，再让服务器的实际运行版本可验证地收敛过去？”

Attempt

⑥ 现在把它当成一道题

你的角色：你是这个仓库的发布负责人。你不能丢掉任何可能有价值的独有提交，也不能直接在生产服务器上用“试试看”的方式解决 48 个冲突。

目标状态：得到一个经过测试、历史来源清楚的权威版本；GitHub main 能解释所有保留改动；106 实际运行版本能被证据证明与该版本一致。

1理解题：为什么 origin/main = 84382576 和 HEAD = c5e35ae 可以同时成立？请用“指针”语言解释。

2诊断题：五个对象里，哪些是“权威状态”、哪些是“需要先保护的独有历史”、哪些只是“临时/参考状态”？

3风险题：如果现在只能先做一件事，什么类型的操作最危险、最不应该先做？为什么？

4方案题：不要写具体命令。请设计 5 个有顺序的阶段，把这三个主要状态安全收敛。每阶段写“处理对象 + 目的”。

5验证题：最后你要收集哪些可观察证据，才能说“GitHub 主线、服务器 checkout、真实线上运行版本都一致了”？至少写 4 条。

Hint

⑦ 分级提示

每次只看一级。下一层提示只有在你主动点击后才出现。

Hint 1 · 方向

先不要想“pull 还是 reset”。先问两个问题：哪些提交只有一个地方有？哪个指针只是缓存而不是实际 checkout？

Hint 2 · 结构

一个成熟流程通常遵循：盘点快照 → 保护独有历史 → 在非生产环境做集成 → 测试 → 部署 → 验证。把你的三个主要状态分别放进这些阶段。

Hint 3 · 接近答案

不要先改 106。先确保服务器那 1 个独有提交和前端 66 个独有提交都有可恢复的引用；再以最新 GitHub main 为集成基线，专门处理前端冲突与测试。只有当主线版本验证完成，才轮到服务器 checkout 与真实运行版本收敛。
